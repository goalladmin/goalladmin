# 决策记录

规范没写清、或实现时偏离了规范的取舍都记在这里。一条一段：日期、问题、选择、理由。新条目追加在末尾。"规范"指 `docs/spec.md`，章节号与它一致。

## D-001 · 2026-09-26 · 数据库迁移不用 goose，用内置的 SQL 迁移器

问题：规范 §2 选 pressly/goose 做迁移。

选择：在 `core/db` 里实现一个约 200 行的迁移器（`MigrateUp`、`MigrateStatus`），只支持"按编号顺序、只向前、纯 SQL"的迁移文件；goose 不引入。

理由：goose v3 的 go.mod 把 ClickHouse、PostgreSQL、SQLite、Vertica、YDB 等驱动都列为依赖，引入后每个使用 GoAllAdmin 的项目都会继承一份臃肿的模块图和供应链面。v0.1 只需要"向前执行编号 SQL 并记录版本"，自己实现更小、更容易审计，也没有第三方许可证和版本升级的负担。goose 的 Down 迁移和 Go 迁移在 v0.1 不需要。迁移文件格式保持简单：`NNNNN_name.sql`，语句以行尾 `;` 分隔，不支持 `DELIMITER`。规范 §2、§3.2 的 goose 字样按本条理解。

## D-002 · 2026-09-26 · 依赖版本来源

问题：开发环境无法访问 proxy.golang.org。

选择：直接依赖固定为 gin v1.12.0、gorm v1.31.2、gorm mysql 驱动 v1.6.0、casbin v3.11.0、viper v1.21.0、golang-jwt v5.3.1、validator v10.30.5、x/crypto v0.57.0、testify v1.12.1、base64Captcha v1.3.8（D-029 起改用自带的验证码，不再依赖它）；间接依赖由 `go mod tidy` 解析。发布 v0.1.0 前在有正常网络的环境里把全部直接依赖升到当时的最新版并跑过 `govulncheck`：新版 gin 带进了 `quic-go`（HTTP/3 支持，本项目不用），其 v0.59.0 有已公布的安全公告，已提到修复版；`go get` 因此把 `go.mod` 的 `go` 指令提到 `1.26.0`，最低 Go 版本随之从 1.24 改为 1.26。

理由：这些都是各自主线上的稳定版本，与规范 §2 的版本范围一致。CI 里的 `make vuln` 会在每次推送时重新检查，间接依赖出现安全公告时按同样方式提版本。

## D-003 · 2026-09-26 · HTTP 中间件放在 `core/internal/middleware`，`httpx` 只放业务代码会用到的东西

问题：规范 §3.2 把"请求 ID、恢复、请求体上限、安全头"列在 `httpx` 名下，又要求实现细节进 `core/internal`。

选择：`httpx` 公开包只包含业务代码需要的：响应信封、错误类型与错误码、分页、参数绑定、请求 ID 读取。中间件实现在 `core/internal/middleware`，由 `core/app` 装配。

理由：业务代码从来不需要直接引用中间件；把它们藏进 internal 缩小公开 API 面（规范 §16.2）。

## D-004 · 2026-09-26 · 错误码里协议层错误的取值

问题：规范 §9.2 的错误码分段没有给"路由不存在、方法不允许、请求体过大、限流"这些协议层错误分配号段。

选择：放在 4000 段的尾部，用与 HTTP 状态码对应的后三位：4004 资源或路由不存在、4005 方法不允许、4013 请求体过大、4029 请求过多。4001 起的普通框架业务错误码按规范不变。

理由：一眼能看出对应的 HTTP 状态；不占用认证、授权、校验段。

## D-005 · 2026-09-26 · `db.From(ctx)` 依赖 ctx 里的数据库句柄

问题：规范 §3.4 要求 `db.From(ctx)` 且禁止包级全局变量，两者需要一个把句柄带到 ctx 的机制。

选择：`app` 在每个请求的 ctx 和传给 `Module.Start` 的 ctx 里放入 `*gorm.DB`（`db.WithDB`）。`db.From(ctx)` 优先返回 ctx 里的事务句柄，其次返回基础句柄；两者都没有时 panic，提示"ctx 不是由 app 创建的"。

理由：这是不引入全局变量的最简单方案；CLI 命令和测试可以自己 `db.WithDB(ctx, gdb)`。

## D-006 · 2026-09-26 · 容器健康检查用二进制自带的 `healthcheck` 子命令

问题：运行镜像是 distroless，没有 curl。

选择：`server healthcheck` 子命令请求本机 `/healthz`，成功退出码 0。

理由：不为健康检查引入 shell 或 curl。

## D-007 · 2026-09-26 · 实体表底部固定块

问题：各表的状态、排序、备注、时间、操作人列此前各排各的。

选择：所有实体表底部固定为 `status, sort, remark, created_at, updated_at[, deleted_at], created_by, updated_by[, deleted_by]`，规则写在 `docs/conventions.md`。`deleted_*` 只出现在软删表上；框架表不软删。日志表只有 `created_at`，关系表没有时间列。

理由：列位置固定后，通用列表页、代码生成和人工审阅都不用逐表确认；软删列按需出现是为了避免唯一索引被已删除行占住。

## D-008 · 2026-09-26 · 修改密码保留当前会话；锁定判定先于限流

问题：规范 §5.4 写"修改密码吊销该用户的全部会话"；§5.7 的限流和锁定没有规定先后。

选择：用户自己修改密码时吊销其他会话、保留当前会话；管理员重置密码时吊销全部。登录时先判断锁定再判断限流。

理由：强制改密的用户改完密码立刻能继续用，不必再登录一次，而安全目标（让其他地方的会话失效）不受影响。被锁定的账号得到"锁定到何时"的明确提示，比 429 更有用；锁定期间的请求被拒得很便宜，不需要再靠限流保护。

## D-009 · 2026-09-26 · Casbin 只做判定引擎，策略读写走自己的只读适配器

问题：规范 §2 选 casbin + gorm-adapter 存储策略。

选择：引入 casbin 核心库做判定（模型见 `core/rbac/enforcer.go`），策略表 `ga_casbin_rule` 保持 gorm-adapter 的列结构，但读写由 `core/rbac` 自己完成：写入在业务事务里落库，之后整体 `LoadPolicy` 重载；适配器只实现 LoadPolicy，其余方法拒绝。不引入 gorm-adapter。

理由：gorm-adapter 的 go.mod 把 PostgreSQL、SQL Server、SQLite 驱动都列为依赖（同 D-001 的问题）。自己写读写还能让"改角色权限"和其他表的变更在同一个事务里，避免库和内存不一致。表结构与 gorm-adapter 兼容，将来需要时可以无缝换回。

## D-010 · 2026-09-26 · 权限判定不用 Casbin 的 g（角色继承）

问题：规范 §6.3 已写明不用 g；这里记录实现层面的推论。

选择：用户的启用角色列表带 15 秒缓存（用户角色变更、角色停用时主动失效）；判定时对每个角色各 Enforce 一次；超管在认证中间件里就已标记，Require 中间件直接放行。未注册的权限码在判定入口直接返回 false，策略表里的脏数据不会产生授权效果。

理由：一个数据源（`ga_user_role`）、一个判定路径，行为容易推理和测试。

## D-011 · 2026-09-26 · 操作日志的实现放在 `core/internal/oplogimpl`，`core/oplog` 只是门面

问题：规范 §10 要求 `oplog.Record` 作为路由选项挂在业务路由上；同时框架自己挂的 `PUT /auth/password` 也应该记日志。`oplog.Record` 返回 `app.RouteOption`，所以 `core/oplog` 必须 import `core/app`，`core/app` 就不能反过来 import `core/oplog`。

选择：中间件、脱敏、落库、查询都在 `core/internal/oplogimpl`；`core/oplog` 公开包只提供 `Record`、`List`、`IsSensitiveKey` 和类型别名。`core/app` 直接用内部包给 `/auth/password` 挂日志（动作名 `auth.password`）。

附带的取舍：一、中间件排在守卫之后，所以只记"通过了认证和授权的请求"，401/403 不进操作日志（登录失败有登录日志）；二、落库是同步的，但用 `context.WithoutCancel` 去掉请求 ctx 的取消信号，客户端中途断开也能写完；三、写库失败只记错误日志，不改变已经发出的响应；四、动作名建议用 `<资源>.<动作>` 的稳定编码（如 `user.create`），由前端按语言翻译，库里不存中文；五、请求体只解析 JSON 和表单，其他类型只存 `<类型, 大小>` 占位，解析失败的 JSON 也不存原文（可能含明文密码）；六、脱敏在截断之前做，密钥不会被截在 4 KB 边界上漏出来。

理由：一次 import 方向的约束，换来框架路由和业务路由用同一套日志实现；后面几条都是"宁可少记，不可漏密"。

## D-012 · 2026-09-26 · 业务表照 D-007 的底部固定块，软删写法在新增模块指南里演示

问题：业务表要不要软删、软删的列放在哪里，规范没有写；各模块各写各的，`deleted_by` 这类列最容易漏。

选择：业务表按 D-007：业务列之后接 `status, sort, remark, created_at, updated_at[, deleted_at], created_by, updated_by[, deleted_by]`。需要软删的表删除时写 `deleted_at` 和 `deleted_by`，模型用 `gorm.DeletedAt` 让查询自动排除已删行；不软删的表不要这两列。`docs/guides/new-module.md` 用订单模块演示完整写法，查询和更新可以对照系统模块里的岗位（硬删）。

理由：业务表大多需要软删和操作人，指南里演示一次，业务方就不用各自摸索 `deleted_by` 怎么写。

## D-014 · 2026-09-27 · `@ga/shell` 以源码形式被端引用，不单独打包

问题：规范 §3.5 把壳定义为独立包，但没说它是发布物还是工作区内的源码包。

选择：`@ga/shell` 的 `exports` 直接指向 `src/index.ts` 和 `src/styles/index.css`，各端通过 `workspace:*` 引用，Vite 与 vue-tsc 都按源码解析；壳的 `build` 脚本是空操作。Element Plus 采用全量引入（`app.use(ElementPlus)`）并全局注册全部图标，业务页面不用配置自动引入插件。

理由：v0.1 只有一个仓库、一个工作区，源码引用省掉了库模式打包、类型声明生成和版本发布这一整套流程，改壳即时生效；`exports` 仍然把深层路径挡住了，公开 API 面的约束不变。全量引入让首包约 1.3 MB（gzip 约 420 KB），后台系统可以接受；需要瘦身时再引入按需加载，那是纯工程改动，不影响业务代码。壳要作为 npm 包发布时再加库模式构建。

## D-015 · 2026-09-27 · 文案键的解析规则与操作日志动作名

问题：后端菜单用 `menu.system`（目录）和 `menu.system.user`（页面）两种键，vue-i18n 默认按点下钻，嵌套对象里放不下"既是字符串又有子键"的节点。

选择：自定义 `messageResolver`：每一层先把剩余路径当作一个整体键查（允许 `'system.user'` 这样带点的键），查不到再按第一段下钻。端的文案文件因此可以写成 `menu: { system: '系统管理', 'system.user': '用户管理' }`。操作日志的动作名在库里是稳定编码（`user.create`），前端用 `op.<action>` 查翻译，没有翻译就显示编码本身。

理由：不改后端的键设计（目录和页面的键有天然层级关系，前端按此推导面包屑），也不要求文案文件绕着写；解析规则有单元测试。

## D-016 · 2026-09-27 · 前端工作区同时支持 pnpm 和 npm，锁文件以 pnpm 为准

问题：规范 §2 只提 pnpm；日常开发有人习惯 npm。

选择：工作区同时声明 `pnpm-workspace.yaml` 和 `package.json` 的 `workspaces`；`apps/platform` 用版本号 `"@ga/shell": "0.1.0"` 引用壳（不用 `workspace:*`，npm 不认），pnpm 通过 `linkWorkspacePackages: true` 链接本地目录；根目录脚本用 npm 的工作区语法（`npm run x --workspaces --if-present`、`-w @ga/platform`），pnpm 调用时照样能跑；`.npmrc` 只放两者都认识的键，其中 `legacy-peer-deps=true` 是为了绕开 npm 10 解析 vitest 可选 peer 依赖环时的崩溃（npm 11 起已修；所有 peer 都已显式锁定，关掉自动 peer 解析没有副作用），pnpm 忽略它。可复现安装以 `pnpm-lock.yaml` 为准：CI 与 Docker 镜像用 `pnpm install --frozen-lockfile`，`package-lock.json` 加入忽略清单；加依赖用 pnpm，锁文件才会更新。`minimumReleaseAge` 只对 pnpm 生效。

理由：两个包管理器都能装、能跑、能测（已各自验证 lint、typecheck、vitest、build、Playwright），而只维护一份锁文件，避免两份锁漂移。

## D-017 · 2026-09-27 · 机密允许写在不进 git 的 `config.yaml` 里，环境变量优先

问题：规范 §11.1 原文写"所有机密只能来自环境变量，配置文件里不留位置"。本地开发每次都要 export 密码和密钥，不如一个文件省事；而 `config.yaml` 本来就在 `.gitignore` 里。

选择：`database.password` 和 `portals.<code>.jwtSecret` 可以写在 `config.yaml` 里，对应的环境变量 `GA_DB_PASSWORD`、`GA_JWT_SECRET_<CODE>` 一旦设置就覆盖文件里的值。`config.example.yaml` 给出这两个键但留空。release 模式的启动校验不变：密钥长度、示例值、各端不同、密码非空，无论来自文件还是环境变量都要过。

理由：安全目标是"机密不进仓库、不进镜像"，靠 `.gitignore` 排除 `config.yaml` 和容器部署只用环境变量就能达到；把本地开发也逼到环境变量上只增加摩擦。§11.1 按本条理解。

## D-018 · 2026-09-27 · 入口放在 `server/main.go`，不带子命令等于 `serve`

问题：规范 §3.2 把入口放在 `server/cmd/server/main.go`。这是 Go 里多个二进制共存时的惯例，但本项目只有一个二进制，`go run ./cmd/server serve` 比必要的长。

选择：`main.go` 直接放在 `server/` 根目录，`go run .`、`go run main.go` 都能启动；不带子命令或第一个参数是选项时视为 `serve`，其余子命令不变。构建产物名仍是 `server`（`.gitignore` 已排除 `/server/server`）。将来真的需要第二个二进制时再建 `cmd/` 目录，依赖方向检查的规则 4 同时覆盖根包和 `cmd/*`。

理由：一个二进制用不着 `cmd/` 这层目录；启动命令越短，README 的"10 分钟跑起来"越可信。

## D-019 · 2026-09-27 · 迁移文件必须可重跑

问题：迁移器把一个文件放在一个事务里执行，但 MySQL 的 DDL 会隐式提交。文件中途失败时，前面的 `CREATE TABLE` 已经生效而版本表没有记录，重跑从第一条开始就报"表已存在"，真正失败的那条语句反而被挡住看不到。本机首次跑迁移时就遇到了这个情况。

选择：不改迁移器的事务模型（MySQL 上做不到 DDL 回滚），改约定：所有迁移文件写成可重复执行的——`CREATE TABLE IF NOT EXISTS`、种子数据 `INSERT ... ON DUPLICATE KEY UPDATE`、加列前判断或拆成小文件。框架的初始迁移按此编写，规则写进 `docs/guides/new-module.md`，`core/db/migrate.go` 里有注释说明原因。

理由：这是 MySQL 迁移的通用做法；可重跑的文件让"失败 → 修 → 再跑"的循环不需要手工清库，也让真正的错误暴露在第一时间。

## D-020 · 2026-09-27 · 授权边界的五条收紧

问题：规范 §6.4、§6.5 写明了超管与敏感权限的规则。规则不能只落在最直接的入口上：分配角色、会话所属的端、账号状态这几条间接路径要同样覆盖；部署示例的默认值也要是安全的那一个。

选择：

1. 非超管分配角色时，新加的角色不能含敏感权限码、不能含自己没有的权限码，也不能改动超管账号的角色——与授权（`GrantRolePerms`）同一条规则——分配一个含敏感权限的角色，效果和直接授出敏感权限相同。目标用户已有的角色不算新加，整体替换时保留原角色不受影响。测试 `TestRBAC_14b`。
2. 刷新凭证和访问令牌对应的会话都必须属于当前端：`session.Rotate` 带端参数，会话不属于该端按不存在处理。当前只有一个端，这是启用第二个端前必须有的边界。测试 `TestAuth_RefreshRejectsSessionFromAnotherPortal`。
3. "最后一个可用超管"的判定要看账号状态：`rbac.Service` 持有端注册表，停用的超管不算数：停用的账号登录不了，算进"还剩几个超管"没有意义。测试 `TestRBAC_15b`。
4. Compose 里 `trustedProxies` 默认只信任固定 IP（172.30.0.10）的 nginx 容器，而不是整段私网；nginx 把 `X-Forwarded-For` 设成 `$remote_addr`（覆盖而非追加），客户端自带的转发头一律丢弃，按 IP 的登录限流看到的是真实来源。
5. 构建镜像用仍在安全维护期内的 Go（`golang:1.27.x-alpine`），CI 用 `setup-go` 的 `stable`；`go.mod` 的 `go` 指令保留为最低语言版本，不跟着构建镜像走。

理由：前三条都是"低权限账号扩大自己权限"这一类路径，正是规范 §6.5、§13 反复强调要用反向测试堵住的；后两条是部署默认值，脚手架的默认值应当是安全的那一个。

## D-021 · 2026-09-27 · 端边界、构建上下文与 HTTP 超时

问题：多端是脚手架的承诺，角色和会话的接口要以端为界，即使 v0.1 只有一个端；Docker 构建上下文要排除哪些文件、HTTP 服务器的各项超时取什么值，也要定下来。

理由：前三条是启用第二个端之前必须已经存在的边界，各自只是一个查询条件和一个参数，现在就做比以后再补便宜得多；后两条与 D-020 第 4、5 条同一个原则。

## D-023 · 2026-09-28 · 字典：代码声明与后台维护共用一张表

问题：规范 §1.3 把"字典管理"列在 v0.1 不做的清单里。实际业务里，订单状态、支付渠道这类枚举既要在代码里判断，又要在页面上显示成文字、做成下拉和彩色标签；另有银行列表、行业分类这类运营自己维护、代码不判断的列表。只做后台可编辑的字典表，代码依赖的值会被随手改掉；只在代码里写常量，前端就得各写一份对照表，还做不了中英文。

选择：提供字典，框架内核实现，系统管理模块提供管理页面。

1. **两种来源，一张表。** 模块实现可选接口 `app.DictSource`，在代码里声明字典（`dict.Dict`）；启动时同步进 `ga_dict`、`ga_dict_item`，标记为代码来源。后台也可以新建字典，完全可编辑。代码声明的字典编码必须以"模块名 + 点"开头（`order.priority`），后台新建的字典编码不能含点，两者的命名空间天然不冲突。
2. **代码拥有值，后台拥有显示。** 代码字典的字典本身、项的集合、值、层级都由代码决定：后台不能删项、不能加项、不能改值。后台能改项的显示文字（含英文）、颜色、扩展值、排序、备注和启用状态；改过的项记 `overridden = 1`，之后代码里的文字变了也不覆盖，可以"恢复默认"。代码里删掉的项不删行（历史数据还要靠它显示），改成后台可编辑并停用，启动日志里提示。代码里不再声明的整本字典同样转为后台字典，由管理员决定是否删除。
3. **值类型。** 字典声明 `string` 或 `int`；库里统一存字符串，读取接口按类型输出 JSON 字符串或数字，前端拿到的值与业务接口里的字段可以直接用 `===` 比较。`int` 字典的值写入时校验必须是整数。
4. **多语言。** 每项存一个默认文字（中文）和其他语言的 JSON 对照表；读取接口按 `Accept-Language` 返回一种语言，前端不需要为字典另写文案文件。
5. **端边界。** 每本字典属于一个端，或 `*` 表示所有端共用。读取接口 `GET /api/<portal>/v1/dicts?codes=` 登录即可访问，只返回属于当前端或共用的、启用中的字典；别的端的字典当作不存在。管理接口只在平台端，可以维护任何端的字典。
6. **层级。** 项可以有父项（`parent_id`），父项创建后不可修改，删除有子项的项会被拒绝，因此不会出现环。
7. **启用状态。** 停用的项仍然随读取接口返回（历史数据要显示文字），前端下拉只列启用的项；服务端校验 `dict.Service.Has` 也只认启用的项。
8. **编码和值按字节比较。** `ga_dict.code`、`ga_dict_item.value` 两列用 `utf8mb4_bin`，偏离 `docs/conventions.md` 的统一排序规则：它们是标识符，用 `utf8mb4_0900_ai_ci` 的话 `e` 与 `é`、`ss` 与 `ß` 会被唯一键当成同一个值，而 Go 代码里的比较认为不同，声明能通过校验、同步时却撞唯一键导致启动失败；读取接口里 `DEMO.X` 也会查到 `demo.x` 却绕开它的缓存失效。按字节比较后两边口径一致：大小写、重音不同就是不同的值。
9. **缓存。** 读取带进程内缓存，写入在事务提交后清掉并把该编码的"代数"加一；读库前记下代数，读完发现变了就不回填，旧数据不会在清缓存之后又被填回去。"不存在"不缓存，格式不合法的编码直接当作不存在、不查库。启动同步用 MySQL 会话锁串行化，多个实例同时启动不会互相踩。
10. **不做**：导入导出、按字典的细粒度权限、字典变更的历史版本。需要时再加。

理由：这与"权限码和菜单在代码里声明"是同一个思路——代码依赖的东西跟着代码走、能评审、能测试，AI 也看得见；运营需要调整的显示层留给后台。一张表两种来源，前端只有一种取法（`useDict`），不必分别维护"枚举"和"字典"两套机制。规范 §1.3"不做"清单里的"字典管理"按本条理解。

## D-024 · 2026-09-28 · 登录防护与密码策略按端配置，只能在底线之内调整

问题：规范 §5.6、§5.7 的阈值写死在代码默认值里（`portal.LoginPolicy`、密码最短 10 位），部署方要调只能改代码；而支付、金融类部署常常要求更严的密码（大写、符号、定期更换）或更严的锁定。同时，常见的做法是把这些参数做成后台网页上可开可关的开关，默认关闭——超管会话一旦被盗，第一件事就是关掉锁定和限流。

选择：

1. 配置文件里按端提供 `portals.<code>.login`（出验证码的次数、每次都要验证码、锁定次数、账号锁定次数、锁定时长、统计窗口、每 IP 和每账号的频率）和 `portals.<code>.password`（最短长度、要求大写 / 小写 / 符号、有效期天数）。不写或写 0 表示沿用代码里的值；代码里注册端时也可以给自己的默认值。数值项配置覆盖代码，开关项只能打开。
2. **没有关闭限流、锁定、强制改密的开关。** 每一项都有底线（§5.7），合并后的值越界（包括负数）拒绝启动，而不是悄悄换成默认值。
3. "至少包含字母和数字、不等于用户名、不与上一次相同"始终生效，配置只能往上加。系统生成的密码改为至少 20 位且四类字符齐全，满足任何合法策略。
4. 密码有效期默认关闭（现行建议是不强制定期换密码，但部分合规要求在没有二次验证时 90 天一换）。过期按 `ga_user.pwd_changed_at` 判断，为空视为已过期；过期的账号登录照常，但与强制改密走同一条路径：除 `/auth/*` 外一律 403 `2002`，已登录的会话在状态缓存过期后（最长 15 秒）同样被拦下。登录与 `/auth/me` 返回 `pwdExpired` 说明原因。`portal.Account` 新增 `PwdChangedAt`，自定义 `UserProvider` 不填时，开启有效期会让该端所有账号都要求改密。
5. `/auth/me` 下发当前端的密码策略，改密页据此提示和预校验。
6. 安全策略只能通过配置文件改，不提供网页编辑，也不接受环境变量（它们不是机密，容器部署挂载配置文件即可）。

理由：部署方得到了调严的能力，但任何配置都不能把系统调得比底线更松；不做网页开关，超管会话被盗也关不掉防护。

## D-025 · 2026-09-28 · 菜单管理：结构归代码，后台只改显示和位置

问题：菜单由模块在代码里声明（规范 §6.6），改个名字、换个图标、调一下顺序都要改代码重新发版，太重。同类框架的做法是把菜单整张表放进数据库、后台随意增删改，包括路由路径和页面组件；这样授权数据就变成了运行时可改的数据，有菜单管理权限的人能把菜单指向任意页面、配合接口表改写授权，形成提权链，代码升级时库和代码也会对不上。

选择：

1. **结构归代码，后台只改显示。** 能改的：显示名（按语言，留空沿用代码里的翻译键）、图标、同级排序、上级（挪到别的目录或分组下）、在侧边栏隐藏。不能改的：路由路径、页面组件、权限码、所属端、代码里标记的隐藏（只能再隐藏，不能取消代码的隐藏）。接口按显式字段白名单严格解析，请求里带了别的字段（例如 `path`、`component`、`perm`）直接回 3002，不静默忽略。
2. **后台可以建分组。** 分组是纯目录：没有路径、页面和权限码，只用来归类；分组内有可见的子项才显示。分组名由服务端生成（`@g-` 加随机串），代码声明的菜单名改为必须匹配 `^[a-z][a-z0-9-]{0,63}$`，两者不会重名。删除分组时，里面的代码菜单回到代码声明的位置，里面的分组挪到被删分组的上级。**不做**后台新建页面菜单（没有页面代码就没用，还会成为越权面）和外链/内嵌菜单（钓鱼跳转、`javascript:` 地址的风险）。
3. **可见性不受影响。** 菜单是否可见仍只由权限码决定：一个菜单要求的权限码是它自己的权限码加上代码里所有祖先的权限码，只由代码算出，挪到哪里都不变；页面满足即可见，目录和分组还要有可见的子项。于是带权限码的目录（及它的代码子孙目录）只能放它在代码里本来的子项，分组也不能放进这样的目录——否则挪出去的菜单会少要求一个权限码（多给人看到），挪进来的菜单会多要求一个（让本该看到的人看不到）。改名、换图标、挪位置、隐藏都不会让任何人多看到一个菜单或多进一个页面；页面路由按路径注册，挪位置后书签照常可用，面包屑跟着显示位置走。
4. **位置校验在服务端整体做。** 拖动后一次提交该端全部节点的位置，服务端在一个事务里校验：节点集合与当前完全一致（代码刚加了菜单就回 4001，请刷新）；上级必须是同端的目录或分组（菜单在代码里的上级总是可以，例如挂在列表页下的详情页），并满足第 3 条；不能成环；层级不超过 4 层（代码自己声明得更深时以代码为准）。任何一项不合格整体拒绝，不会只存一半。恢复默认、删除分组、新建分组也先算出结果再做同一套校验。
5. **存储。** 只存"与代码不同的部分"，一张表 `ga_menu_custom`：代码菜单的覆盖行（按端 + 菜单名）和分组行。覆盖行不再与代码有差异时删除；代码删掉的菜单，覆盖行自动失效，被引用的上级不存在时回到代码位置。菜单名和上级列用 `utf8mb4_bin`。读取带进程内缓存，写入提交后把该端的代数加一并清缓存；读库期间代数变了就不回填，旧数据不会被填回去。
6. **权限。** 查看 `system:menu:list`；修改 `system:menu:update` 标为敏感权限，只有超管能授给角色。只能管理操作者所在端的菜单。所有修改都记操作日志（`menu.*`）。
7. **图标只校验格式**（`^[A-Z][A-Za-z0-9]{0,63}$`，即图标组件名），不在后端维护图标清单：前端只按名字查内置图标表，查不到就不显示，任意字符串都不会被当作组件或地址加载；这样后端不绑定具体的 UI 组件库。显示名在前端一律按纯文本渲染。

理由：日常调整（改名、换图标、排序、归类）在后台点几下就能完成，而"谁能看到什么、能打开哪个页面"仍然只由代码和角色授权决定，菜单管理不会成为提权入口。

4. **端决定启用哪些语言**：`createPortalApp({ languages })`，默认全部 11 种。浏览器语言自动匹配：先完全匹配，再按语言匹配（`zh-Hant`、`zh-HK`、`zh-MO` 归到繁体，其他 `zh` 归到简体；`ta-SG`、`ms-SG` 这类归到同语言）。**缺翻译时的回退**：繁体先回退简体再回退英文，其他语言回退英文；不会显示成翻译键。
5. **前端每个请求带 `Accept-Language: <当前界面语言>`**，后端按同样的匹配规则选语言，错误码的提示文字 11 种语言齐全，未知语言用英文。
6. **字段错误按键翻译**：`httpx.FieldError` 增加 `key`（如 `rbac.menu.maxDepth`、`validation.max`）和 `params`（如 `{limit: 4}`），`message` 统一为英文说明（给日志、接口调用方和没有翻译时兜底）。前端提示错误时优先用 `err.<key>` 的翻译并代入参数，没有翻译就显示 `message`。翻译只维护在前端文案里，后端不用关心有几种语言。业务模块自己的字段错误按同样方式带键，键以模块名开头。
7. **数据里的多语言**（字典的名称和显示文字、菜单管理里改的显示名）本来就按语言代码存，不改表；管理页的输入框改为按端启用的语言生成。字典读取的回退链与第 4 条相同，最后落到默认语言的文字。
8. **翻译质量**：机器辅助翻译的文案先上，马来语、泰米尔语、孟加拉语等建议交付前请母语使用者校对。所有语言文件由测试保证与简体中文的键完全一致、占位符一致、不含会被当作文案语法的字符。

理由：语言清单集中在一处，加一种语言只需要加文案文件和清单里的一行；错误说明按键翻译后，后端不随语言数量膨胀，前端所有提示都跟随界面语言。

4. **图表用 ECharts（Apache-2.0）**，按需引入需要的图表类型和组件，首页单独成块，其他页面不加载。
5. **第三方许可证**：构建时自动生成 `third-party-licenses.txt`，与 `index.html` 同目录，收录实际打进包里的每个第三方包的许可证和 NOTICE。界面上不显示署名（许可证不要求），但不删除、不改写任何第三方的版权声明。
6. **全局搜索**只搜索当前用户看得到的菜单（来自 `/auth/me`），不访问后端；支持方向键和回车。
7. **偏好设置**（主题色、侧边栏深浅、是否显示标签栏和面包屑、紧凑模式）只影响本浏览器的显示，存在 localStorage，不是敏感数据；可以一键恢复默认。
8. **锁屏在服务端生效**：`POST /auth/lock` 把当前会话标记为锁定（`ga_session.locked_at`）；锁定期间除 `/auth/me`（只返回用户名、头像和 `locked: true`，不返回菜单和权限）、`/auth/unlock`、`/auth/logout`、`/auth/refresh` 外，所有需要登录的接口一律回 1006（HTTP 423）。所以刷新页面、另开标签页、直接调接口都绕不过锁屏。`POST /auth/unlock` 校验当前账号的密码；连续输错 5 次直接吊销这个会话（原因 `unlock_failed`），只能重新登录。每次解锁尝试先在数据库里（行锁）占用一次机会再校验密码，并发发来一批请求也一共只有 5 次机会，用完之后的请求连密码都不校验；密码正确但会话刚被并发的错误尝试吊销的，也不能解锁。输错的次数同时计入登录防护（按账号和 IP），所以换到登录页不会多出猜测的机会，重新登录通常要先过验证码。锁屏后前端卸载当前页面（缓存的标签页一并丢弃）并清掉权限和菜单，锁屏层下面不留着已经显示过的数据；静默请求收到 1006 也会切到锁屏。认证链路的状态缓存加了失效代数：读库期间会话被锁定或吊销时，读到的旧状态不会写回缓存。锁定和解锁都记操作日志（`auth.lock`、`auth.unlock`，请求体里的密码照常打码）。

理由：界面观感对"开箱即用"的第一印象影响很大；概览页用真实数据，既有用又不误导；锁屏如果只在前端做，刷新页面就能绕过，没有意义，所以放在会话上由服务端判定。

## D-028 · 2026-09-28 · 构建产物随附第三方许可证声明

问题：MIT、BSD、Apache-2.0 等许可证都要求分发软件时附带版权和许可声明。仓库本身只有本项目的代码（依赖只以锁文件、`go.sum` 引用，不在仓库里），但前端构建产物、后端二进制和两个 Docker 镜像都包含第三方代码。前端产物在 D-027 已经附了清单；后端二进制和镜像还没有，本项目自己的 `LICENSE`、`NOTICE` 也没有进镜像。

理由：声明随产物走，无论谁拿到二进制、镜像或前端文件，都能看到其中第三方组件的许可证；由构建生成而不是手写，依赖升级后不会过时。

## D-029 · 2026-09-28 · 用自带的数字验证码替换 base64Captcha

问题：生成第三方许可证清单（D-028）时发现，验证码库 `mojocn/base64Captcha` 会把自带的 11 个字体文件（约 5.8 MB）整体嵌进 `server` 二进制，而本项目只用它的数字验证码，数字验证码并不用字体。这些字体在该模块里没有任何许可证说明；它间接依赖的 `golang/freetype` 是 FreeType 许可证或 GPL-2.0 二选一。两者都不在规范 §2 的许可证白名单里，也写不出准确的许可声明。

选择：`core/internal/captcha` 自己实现，只用 Go 标准库，对外接口不变（`New`、`Generate`、`Verify`，测试用的 `Peek`）：

1. 答案是 5 位数字、ID 是 20 字节随机数，都取自 `crypto/rand`。
2. 答案存进程内存（v0.1 单实例），5 分钟过期，最多 10240 个；满了先丢最早生成的。校验时无论对错都作废这个 ID，比较用常数时间。
3. 图片 140×48 PNG，以 data URL 返回（与原来相同，前端不用改）：数字用本项目自己定义的 5×7 点阵，每位随机缩放、旋转、错位，每个点随机抖动；整张图做正弦波扭曲，再加干扰曲线和噪点；颜色每张随机。

依赖因此去掉 `mojocn/base64Captcha`、`golang/freetype`、`golang.org/x/image`，二进制小约 6 MB。

理由：验证码只是登录防护里的减速带（真正的防线是限流和失败锁定，规范 §5.7），自己写一百多行就够用；换来的是依赖许可证全部在白名单内、二进制里没有来源不明的文件。

## D-031 · 2026-09-28 · 监控中心加固：短缓存、服务器状态开关、版本号只到大版本

问题：D-030 的监控中心每个打开页面的浏览器都会定时刷新。服务器状态每 5 秒读一次内存统计（会让程序极短地停顿）并测一次数据库连接；安全统计每 30 秒对登录日志做几条统计查询。同时开页面的人越多，负载越大，没有上限。另外，实测数据库版本返回 `8.0.46-0ubuntu0.24.04.4`，连服务器的操作系统和补丁号都带了出来，账号一旦被盗，这类信息能帮攻击者对照公开的安全公告挑选下手的地方。有的部署对安全要求高，希望连超管也看不到服务器状态。

选择：

1. **短缓存，放在进程内**：
   - 服务器状态缓存 2 秒（`monitor.serverCache`），安全统计按端缓存 10 秒（`monitor.securityCache`）。取值范围 0 到 1 分钟，0 表示不缓存。
   - 不论多少人同时打开页面，每个进程每个周期最多各算一次。
   - 以后接入 Redis 也保持进程内缓存：服务器状态本来就是"这个进程自己"的数据，不能放进多台共享的缓存；安全统计在多台部署时每台各查一次，压力仍然有上限。
2. **开关 `monitor.server`**，默认 `true`：
   - 设为 `false` 时不采集请求统计（中间件不挂），`GET /system/monitor/server` 只返回 `{enabled: false}`，页面只显示安全态势。
   - 安全态势不受影响。
3. **第三方组件的版本号只到大版本**：Go 显示 `go1.26`，MySQL 显示 `8.0`（MariaDB 显示 `10.11 MariaDB`），去掉补丁号和发行版后缀。
   - 本项目自己的构建版本照常显示。
   - 需要精确版本时去服务器上查，不从网页看。

理由：缓存让负载有固定上限，代价只是数据最多晚几秒；开关让部署方自己决定要不要这块信息；版本号截短后，运维判断"该不该升级"仍然够用，泄露的细节少很多。

## D-032 · 2026-09-28 · 运维中心与安全审计：错误日志、安全事件、调查时间线、查看留痕，日志一律不可删除

问题：
- 现有的操作日志只记"通过了权限检查"的请求。越权被拒（403）、伪造令牌、刷新凭证重放、来源校验失败，要么只写进日志输出，要么什么都不留，后台查不到。
- 程序出错（5xx、panic）只在日志输出里，没有日志系统的部署看不到"系统哪里坏了"。
- 登录日志、操作日志之间没有共同的会话标识，出了事只能按时间手工对照，还原不出"从哪里进来、进来后做了什么"。
- 谁翻看过审计数据，没有记录。
- 部署方要求：所有日志不允许删除。

选择：

1. **运维中心**：平台端新增菜单目录"运维中心"（`/ops`），放操作日志、登录日志（从系统管理移入，接口路径不变）、错误日志、安全事件、调查时间线。
   - 不做：定时任务、版本导入导出、网页读日志文件、主机级服务器状态（已有进程级的监控中心）、数据权限审计（按部门的数据权限不在 v0.1 范围）。
   - 日志文件交给服务器上的工具或日志采集系统；部署文档说明做法。
2. **日志不可删除、不可修改**：
   - 任何日志都不提供删除或修改接口，也不做自动清理（《网络安全法》要求网络日志留存不少于六个月，默认永久保留）。
   - 反向测试检查所有日志资源只有读取路由。
   - 部署文档建议数据库账号对日志表只授予插入、查询（和汇总需要的更新）权限。
3. **错误日志**（`ga_error_log`）：
   - 只记服务端故障：响应状态 ≥ 500 和 panic；4xx 不记。健康检查不记。
   - 按指纹合并：同一类错误（panic 按类型和出错位置；其他按方法、路由模板、错误码和去掉具体值的错误文本）只占一行，累加次数，保留首次、末次时间和最近一次的请求 ID、用户、会话、IP。
   - 错误文本去掉引号里的值和敏感键的值，截断到 1 KB；panic 的调用栈只保留文件名和行号的最后三级路径，截断到 8 KB。
   - 列表和调用栈分两个权限：`system:errorlog:list`、`system:errorlog:detail`，都是敏感权限。
4. **安全事件**（`ga_security_event`）：
   - 记录攻击迹象：越权被拒（`forbidden`，带权限码）、跨端使用令牌（`cross_portal`）、签名或格式不对的令牌（`token_invalid`）、签名有效但会话和用户对不上（`token_mismatch`，意味着密钥可能泄露）、已吊销会话的令牌仍在使用（`session_revoked`）、刷新凭证重放（`refresh_reuse`）、刷新和登出的来源校验失败（`bad_origin`）、登录被锁定或限流（`login_locked`、`login_rate_limited`）、锁屏解锁次数用完（`unlock_exhausted`）、命令行操作（`cli`：创建管理员、清理策略）。
   - 过期令牌（只有过期、受众和签发方都对）、没带令牌、会话到最长寿命自然过期、密码输错不算安全事件（输错已在登录日志里）；签名有效但主体或会话字段不合规的令牌按 `token_mismatch` 记。
   - 每类事件有固定级别：提示、警告、严重。
   - 防刷库：同一来源（端、类型、用户、会话、IP、方法、路径、说明）在同一分钟内合并成一行、累加次数；同一行每秒最多写一次库，其余次数攒着，由后台每秒写一次，关停前写完；新来源的写库速度有上限（每秒 20 个），超出的只进日志输出。写库失败的次数放回去，下次再写。严重事件不受新来源写入速度的限制，攻击者刷别的事件挤不掉它们；登录类事件的账号由攻击者填写，不参与合并，只保留第一次的账号。错误日志用同样的方式合并（panic 视为严重）。
   - 权限 `system:secevent:list`，敏感权限。业务模块可以通过 `Deps.Audit` 自己记录安全事件。
5. **同时写一份到日志输出**：登录日志、操作日志、安全事件每写一条，同时往日志输出写一行结构化记录（`audit.login`、`audit.operation`、`audit.security`），交给外部日志系统保存。数据库被删改时，外部还有一份。
6. **会话标识和调查时间线**：
   - 登录日志、操作日志、安全事件都记会话 ID（`session_id`，即会话列表里已经展示的 `sid`）。
   - 调查时间线按用户、IP 或会话，把登录日志、操作日志、安全事件合成一条按时间倒序的线，一次最多 200 条，用（时间，类型，ID）组成的游标往前翻，同一毫秒的记录不漏不重。不属于任何端的安全事件（命令行清理策略）也列出。
   - 错误日志不进时间线：它是按指纹合并的系统故障，不是某个人的动作；需要时按请求 ID 对照。
   - 权限 `system:audit:timeline`，敏感权限。
7. **查看留痕**：查看操作日志、登录日志、错误日志列表和详情、安全事件、调查时间线，本身都记一条操作日志（动作名 `audit.view.*`，带查询条件）。

理由：
- 越权尝试和凭证异常是入侵最早、最明确的信号，必须能在后台查到，还要能按人、按 IP、按会话串起来。
- 合并加限速让日志量有上限：攻击者刷接口时，写库次数不会跟着请求数涨，数据库不会先被日志写满。
- 同时写日志输出成本很低，却是数据库被攻破后唯一还可信的记录。
- 删除和修改接口一律不提供，比"只有超管能删"更简单也更可靠：后台账号被盗时，攻击者抹不掉痕迹。
- 错误日志合并成"一类错误一行"，既能回答"系统哪里坏了、多频繁"，又不会在事故时刷库；细节按请求 ID 去日志系统查。

问题：规范 §1.3 把"部门与岗位""按部门的数据权限"列在 v0.1 不做的清单里（§7.2 写着"不在计划内"）。部署方要求补上部门管理和岗位管理。两者常常和"按部门的数据权限"一起出现，而数据权限会影响以后每个模块的查询，是防越权里最重的一块。

1. **范围**：这次只做组织结构——部门树、岗位、用户的部门和岗位归属。部门和岗位只是资料和展示用，**不影响任何权限判断**，权限仍然只看角色授予的权限码。按部门的数据权限作为下一项单独讨论设计；§1.3 的"不做"清单改为只列"按部门的数据权限"，§7.2 改为"待定，单独决策"。

   - 有下级部门或还有用户的部门不能删除；停用的部门不能再分配给用户（已在其中的用户不受影响）。
   - 改动部门树（新建、移动、删除）时在事务里锁住整张部门表再校验，两个管理员同时挪部门也不会成环；给用户分配部门时对部门行加共享锁，与删除部门互斥。删除时统计人数用普通读（部门行已排他锁住，快照在拿到锁之后建立），不锁用户行，避免和编辑用户互相等待。编辑用户时先锁住用户行，岗位只写差异。
   - 新选的负责人必须是启用的用户；原来的负责人后来停用了，编辑部门时可以保留。
3. **岗位**（`ga_post`）：`code`（小写字母开头，只含小写字母、数字、连字符，创建后不可改）、`name`，加底部固定块，不软删。还有用户在用的岗位不能删除；停用的岗位不能再分配。
4. **用户归属**：每个用户最多属于一个部门（`ga_user.dept_id`，0 表示未分配）；可以有多个岗位（`ga_user_post`，最多 20 个），整体替换。创建、编辑用户时一并提交；用户列表可以按部门筛选，默认包括下级部门。
5. **权限**：`system:dept:list/create/update/delete`、`system:post:list/create/update/delete`，都不是敏感权限（只是资料）。用户表单用的部门、岗位下拉接口要 `system:user:list`，不对所有登录用户开放。以后做数据权限时，"改用户的部门"会变成影响可见范围的操作，届时重新评估是否敏感。
6. **操作日志**：`dept.create/update/delete`、`post.create/update/delete`；用户的部门、岗位随 `user.create`、`user.update` 记录。

理由：先把组织结构做对、做稳，数据权限单独设计，可以把"数据范围怎么定义、框架怎么强制每个查询都带上、怎么测"想清楚再动手，不在一次改动里同时引入两类风险。部门、岗位本身不带权限，出错也不会越权。

## D-034 · 2026-09-28 · 系统设置分组与只读的安全设置页

4. **接口** `GET /system/security-policy`：只返回操作者所在端的生效策略。生效值由认证器提供（代码声明叠加配置文件并通过底线校验后的结果，与登录时实际使用的是同一份），`auth.Service` 新增只读方法 `Policies`。不返回 JWT 密钥、数据库等任何机密配置，也不返回配置文件路径。

理由：管理员在后台就能看清当前的防护强度和该去改哪一项，合规检查时也有据可查；而修改仍然要求能登录服务器，偷到一个浏览器会话的人既关不掉防护，也调不松。

## D-035 · 2026-09-28 · 超管账号保护：重置密码只归超管，超管的密码只能在命令行重置

问题：重置别人的密码等于"能用对方的账号登录"。如果它是一个能授给普通角色的权限码，拿到它的人（比如 IT 支持）就能重置权限比自己高的账号——包括超管——再用新密码登录，横向的管理权限就成了纵向的提权。同理，改资料、启停账号、让会话下线这几类对别人账号的写操作，也不能被非超管用在超管账号上；分配角色已经有"非超管不能动超管账号的角色"（D-020），这里把它补成一条统一的规则。

选择：

1. **网页上的重置密码只有超管能做。** 新增第四档路由守卫 `rbac.RequireSuper()`：登录且是本端超管才放行，否则 403 并记安全事件（`forbidden`，说明为 `super`）。`/users/:id/reset-password` 用它，重置密码没有对应的权限码，不能授给任何角色（迁移 00009 清掉库里可能残留的 `system:user:reset-password` 授权，可以重跑）。读取角色授权时只返回已注册的权限码，删掉某个权限码之后，授权对话框整体提交也不会因为残留被拒，保存一次就清掉了（残留本来就不产生任何权限，也可以用 `server rbac prune` 清理）。
2. **超管的密码谁都不能在网页上重置**，包括别的超管和他自己（自己改密码走"修改密码"，要输入旧密码）：回 403，说明为 `system.user.resetSuper`。
3. **命令行 `server admin reset-password -username NAME`**：能登录服务器的人本来就拥有最高信任。随机生成新密码，只打印一次；下次登录必须改密；吊销这个账号的全部会话（服务进程里的会话缓存最迟 15 秒后生效）；记一条 `cli` 安全事件，说明里带执行命令的系统用户和主机名；安全事件万一没记下来，新密码照样打印出来并给出警告（密码已经换掉，不打印就没人知道了）。适用于任何账号，所以没配邮件、超管忘了密码时也有兜底。登录锁定记在服务进程的内存里，命令行解不了，命令会提示等锁定时长过去或重启服务。
4. **非超管不能对超管账号做任何写操作**：改资料（包括部门、岗位）、启用或停用、分配角色（原有规则）、让他的会话下线，一律 403，说明为 `system.user.superProtected` / `system.session.superProtected`。"是不是超管"直接读库（不走角色缓存），只要拥有超管角色就算，不论角色和账号当前是否启用；超管之间照常可以互相管理（最后一个超管的规则不变）。内置的超管角色本身，非超管也不能改（名字、排序、备注）。这些"是不是超管"的判断都和写入放在同一把超管锁里（`WithSuperLock`，分配角色原有的判断也挪了进去）：超管同时把目标提升为超管时，要么先提升、这里看到后拒绝，要么先改完、提升在后，不会出现"判断时还不是、写入时已经是"。业务层的这些拒绝和守卫的一样记为安全事件（D-032）。
5. **前端**：重置密码按钮只对超管显示，超管账号那一行的按钮置灰并提示"只能在服务器命令行重置"；非超管看到超管账号那一行的编辑、分配角色、启停按钮置灰；会话列表标出超管的会话，非超管的"下线"按钮置灰。前端只是提示，挡住越权的是后端。

理由：重置密码是最直接的"接管账号"手段，只留给超管，超管自己的则只留给服务器；再把"非超管不能碰超管账号"补齐成一条统一规则，横向的管理权限就不会被拿来接管最高权限。代价是用户多了以后重置密码都要找超管，但这是部署方明确要的取舍（防越权优先）。

## D-037 · 2026-09-29 · 数据库故障时的三道保护：连接超时、请求时限、启动等待

问题：服务启动时只 Ping 一次数据库，连不上就退出。进程管理器（systemd、容器编排）一般会把它拉起来重试，所以"启动时数据库还没起来"本身不致命；危险的是运行中数据库"假死"：进程还在、TCP 连接还通，但查询迟迟不回。连接串里没有设读写超时，驱动会一直等下去；请求的 ctx 也没有时限，只有 `server.writeTimeout` 到点后断开客户端连接，而服务端的 handler 和它占着的数据库连接还在等。连接池（默认 50 个）很快被占满，之后所有请求都排队等连接，整个后台看起来像卡死，即使数据库恢复也要等这些卡住的查询自己结束。后台定时任务（安全事件、错误日志的批量写入，权限状态缓存刷新）用的是没有时限的 ctx，同样会卡住。

选择：

1. **连接串默认带超时**：新增 `database.connectTimeout`（建立连接，默认 5s，1s–1m）、`database.readTimeout` / `database.writeTimeout`（单次网络读写，默认 30s，1s–10m），拼进连接串的 `timeout` / `readTimeout` / `writeTimeout`；`database.params` 里已经写了同名参数时以它为准。这是没有时限的后台任务的兜底：数据库不回话，最多等这么久就报错、放回连接。`readTimeout` 不能小于 `server.handlerTimeout`：请求里的查询要先被请求时限取消（回 503），而不是先被读超时掐断连接（回 500）。启动时同步字典用的 MySQL 锁改为每 200ms 试一次、不在服务端等待（最多 30 秒），否则会被读超时掐断。
2. **迁移不受读写超时限制**：大表上的 `ALTER TABLE` 可能跑好几分钟，被读超时掐断会让迁移停在一半。执行迁移时单独开一个只有一条连接的连接池，连接串里不加框架默认的读写超时（`database.params` 里自己写的照样生效），用完就关。
3. **每个请求有总时限**：新增 `server.handlerTimeout`（默认 30s，必须大于 0 且小于 `server.writeTimeout`，这样超时的请求还来得及把响应写回去）。中间件给请求 ctx 加上这个时限，业务代码里所有经过 ctx 的查询到点都会被取消、连接放回池子。因超时失败的请求回 503（错误码 5003 "服务暂时不可用"），而不是 500；错误日志照常记录。请求结束后才写的记录（操作日志、安全事件、错误日志、登录日志）去掉请求的取消信号和时限，但保留 ctx 里的值，不会因为请求已经超时而丢；操作日志和登录日志的这次写入另有 3 秒上限（安全事件、错误日志原本就是 2 秒），数据库不回话时不会拖住已经写好的响应。注意：把 `server.writeTimeout` 调到 30s 或更短时，要同时把 `server.handlerTimeout` 调得比它小，否则拒绝启动（错误信息会指出这一点）。
4. **启动时可以等数据库**：新增 `database.connectWait`（默认 0，最长 10m）。0 表示连不上立即退出（和以前一样，交给进程管理器重启）；大于 0 时每 2 秒重试一次，直到连上或等满，每次失败打一行警告（带已等待的时间，不带密码）。适合数据库和服务同时启动的场景（例如 docker compose 一起拉起）。

五个新配置项都有环境变量：`GA_DB_CONNECT_TIMEOUT`、`GA_DB_READ_TIMEOUT`、`GA_DB_WRITE_TIMEOUT`、`GA_DB_CONNECT_WAIT`、`GA_SERVER_HANDLER_TIMEOUT`。

理由：数据库慢或者假死时，服务应该快速失败、把连接还回去，数据库一恢复就自己恢复，而不是跟着一起卡住；运维看到的是一串 503 和错误日志，而不是一个不响应的进程。启动等待默认关闭，保持"连不上就退出"的直观行为，需要时再打开。

## D-038 · 2026-09-29 · 个人中心：本人自助改资料、只放真实状态的安全设置、页面归端应用

问题：个人信息页只是一张只读的描述列表加一个"修改密码"按钮。部署方要求做成常见后台那样的"个人中心"：左侧头像和菜单，右侧分"基本设置""安全设置""修改密码""新消息提醒"四块，基本设置能保存。框架里没有本人自助改资料的接口（只有管理员的 `PUT /system/users/:id`），`ga_user` 也没有"个人简介"列。参考的版式里，安全设置和新消息提醒是带开关的演示项（密保手机、密保问题、MFA、站内信），这些功能本项目没有（TOTP 在 v0.2），放上开关只会让人以为有这些防护。

选择：

1. **页面归端应用，接口归系统模块。** 壳的 `createPortalApp({ pages: { profile } })` 本来就允许各端替换个人信息页：每个端的用户表字段不同，个人中心显示什么、能改什么由端自己决定。平台端的页面在 `apps/platform/src/views/profile/index.vue`，接口在系统模块：`GET /system/profile`、`PUT /system/profile`、`POST /system/profile/revoke-other-sessions`，都是 AuthOnly，**只读写调用者本人**，不接受任何指定用户的参数。壳里的简单个人信息页保留，作为没有自己写页面的端的默认页；`/auth/me` 不扩展。
2. **本人能改的只有显示名、邮箱、手机、个人简介**（新列 `ga_user.bio`，迁移 00010）。用户名、状态、角色、部门、岗位、头像、排序、备注仍然只有管理员能改：请求按显式字段白名单严格解析，夹带这些字段直接回 3002，不静默忽略。头像不开放自助修改是因为 v0.1 没有文件上传，自填一个外部地址没有意义。邮箱、手机现在只是资料，不参与任何认证流程，所以改它们不算敏感操作；以后做邮件找回密码时，改邮箱必须升级为要输入当前密码的敏感操作（那时再记决定）。显示名、简介与部门名同一套字符校验（不含控制字符和不可见字符）。改完记操作日志 `profile.update`，并让账号状态缓存失效，`/auth/me` 立即看到新显示名。
3. **安全设置只显示真实状态，不放开关。** 账户密码：上次修改时间、生效的密码策略和有效期，"去修改"跳到改密面板；绑定邮箱、手机：已填写的打码显示，没填的显示"未填写"，跳到基本设置；登录会话：当前有效会话数（含本次），可以一键下线其他会话（`revoke-other-sessions`，吊销本人除当前会话外的全部会话，原因 `logout`，记操作日志 `profile.revoke-others`）；二次验证：显示"计划中（v0.2）"，没有开关。没有的防护不假装有。
4. **修改密码面板复用 `PUT /auth/password`**，规则跟着 `/auth/me` 下发的密码策略走，带密码强度条（只是提示，安全以后端校验为准）；强制改密仍走原来的独立页面。
5. **新消息提醒只是本地占位。** 本项目没有站内信，三个开关存在浏览器 localStorage、不影响任何功能，页面上明确写"暂未启用"；等有消息功能时再接后端。这是部署方要求保留版式的取舍。
6. **不做**：自助改头像（等文件上传；D-040 改为可以上传或选内置头像）、密保问题、手机验证、MFA 绑定（v0.2）、注销账号。

理由：个人中心是每个用户都会打开的页面，观感值得做好；但只把"本人改本人"的几项开放出来，权限模型不变——能改别人的仍然只有管理员，能改权限的仍然只有角色授权。安全设置显示真实状态而不是开关，是和 D-034 同一个原则：页面不能暗示系统有它没有的防护。

## D-039 · 2026-09-29 · 按部门的数据权限

问题：D-033 做了部门和岗位，但它们不影响任何权限判断——拿到 `system:user:list` 的人能看到全部用户，拿到 `system:user:update` 的人能改任何人的资料。部署方要的是"部门经理只管自己部门的人"。这一块是防越权里最重的：范围一旦漏掉一个接口（详情、修改、下拉……），就等于没做。规范 §1.3 把它列在"不做"清单里，§7.2 写着"待定"。

选择（方案经部署方确认）：

1. **两层判断。** 权限码管"能不能做这件事"，数据范围管"能对哪些数据做"。数据范围只会收窄权限码，永远不会放宽：没有权限码，范围再宽也进不来。
2. **四种范围**，从窄到宽：仅本人（`self`）、本部门（`dept`）、本部门及下级（`dept_tree`）、全部（`all`）。每种范围都包含"本人"：本部门是"本部门的数据 + 本人的数据"，没分配部门的人按仅本人算。所以四种范围是一条链，谁宽谁窄没有歧义。
3. **范围挂在"角色 × 数据资源"上。** 模块在代码里声明数据资源（内核新增 `rbac.DataResource` 和可选接口 `app.DataResourceSource`）：编码 `<模块>:<资源>`、显示名、受它约束的权限码、默认范围、可选范围。角色上逐个资源选范围，存 `ga_role_data_scope`；没存的按资源声明的默认值。框架第一个数据资源是 `system:user`（用户），约束用户的列表、详情、新建、修改、启停、分配角色、会话的查看和下线。
4. **按权限码合并。** 判断"对某个资源做某件事"的范围时，只看**拥有这个权限码**的那些启用角色，取其中最宽的。这样 A 角色给了"查看用户 + 全部"、B 角色给了"修改用户 + 仅本人"时，查看是全部、修改只能改自己，不会因为合并把修改也放宽成全部。超管永远是全部。
5. **授权时不能放宽到超过自己。** 设置范围属于角色授权（`system:role:grant`，敏感）。非超管给角色加权限码、或者放宽某个资源的范围时，这个角色在该资源上的范围不能比操作人自己在同一权限码上的范围宽；收窄总是允许。非超管给别人分配角色时同样检查（否则可以借一个范围更宽的角色给别人或自己提权）；非超管把停用的角色重新启用时也按分配角色检查（启用等于把它的权限和范围交给所有拥有它的人）。同一角色的并发授权在事务里锁住角色行，检查看到的是已提交的状态。
6. **强制在服务端每个入口。** 用户资源的列表、详情、下拉按"查看用户"的范围过滤；修改、启停、分配角色、会话下线先查目标在不在范围里——不在就回 404（不回 403，免得试探出这个人存在）。新建和改部门时，新部门也必须在范围内；非超管不能改自己的部门（改了就能扩大自己的范围）；把人挪到"未分配"只有全部范围才行；建用户时顺手分配角色，非超管要有分配角色的权限码。写操作成功后的回显只在目标也在"查看用户"范围内时给完整资料（修改范围可能比查看范围宽）。部门负责人只能选"查看用户"范围内的人（否则部门列表上的负责人名字能把范围外的人试出来）。部门下拉、部门树不受限（部门名字不是用户数据）。
7. **改部门上级要全部范围。** 挪动部门会改变谁在谁的"下级"里。非超管只有在用户资源的**每个**权限码上都是全部范围时才能改部门的上级——只看"查看用户"不够：查看是全部、修改是本部门及下级的人，把别的部门挪到自己下面就能改那些人了。改名、改负责人、新建、删除部门不受影响。讨论时想过把 `system:dept:update` 整个改成敏感，但改部门名字这种事不值得只让超管来授，所以只限制改上级这一个动作。
8. **默认值与升级。** `system:user` 的默认范围是**仅本人**：新建的角色勾上用户管理后，要在授权对话框的"数据权限"页签里明确选范围才能看到别人，安全的一侧是默认。升级时迁移给现有的非超管角色写上"全部"，已经在用的角色行为不变。
9. **不管的东西。** 聚合数字（数据中心的用户总数、部门页的人数、登录统计）不按范围过滤——它们不暴露具体的人；审计数据（操作日志、登录日志、安全事件、调查时间线）有各自的敏感权限，也不按部门过滤。部门、负责人字段不自动授权：负责人不会因此多看到任何东西。
10. **给业务模块用。** `rbac.Service.DataFilter(ctx, principal, resource, perm)` 返回过滤条件，`Apply(tx, deptCol, ownerCol)` 加到 GORM 查询上，`Allows(deptID, ownerID)` 判断单条。部门信息从端的 `portal.Portal.Org`（可选的 `OrgProvider`）取，platform 端由系统模块提供；端没有提供时部门类范围按仅本人算。模块声明的数据资源编码必须以模块名开头、只能约束自己的权限码，文案键在 `data.<模块名>.*` 下。
11. **界面**：角色的授权对话框加第二个页签"数据权限"，逐个资源选范围，和功能权限一起保存（一个请求、一个事务，检查按保存后的最终状态做）。

理由：把范围放在"角色 × 资源 × 权限码"上，既能表达"看全部、只改本部门"这类常见需求，合并规则又简单到能一眼看出不会放宽；四种范围是一条链，授权时"不超过自己"才有意义。默认窄、升级时给现有角色写全部，兼顾了安全和不打扰已经在用的部署。强制放在服务端每个入口并用反向测试逐个覆盖（§13.2 第 57–60 条），而不是指望前端隐藏按钮。

## D-040 · 2026-09-29 · 头像：本人上传或选内置头像，管理员只能清除

问题：个人中心（D-038）的头像不能改——当时定的是"等有文件上传再做"，规范 §1.3 也把"文件上传与媒体库"列在不做里。部署方要求头像能改，并且既能上传自己的图片、也能从内置头像里选；管理员在用户管理里只能清除别人的头像。头像如果是任意字符串（通常是外部图片地址），界面直接拿它当 `<img src>`，外部地址就能记录下每个看到它的管理员的 IP 和访问时间，也能随时换成别的图。

选择：

1. **只为头像开一个专用口子，不做通用文件上传。** §1.3 的"文件上传与媒体库"仍然不做。头像不落服务器磁盘，存在数据库新表 `ga_user_avatar`（每人一行：随机的 32 位十六进制键、256×256 大图、64×64 小图），迁移 00012。
2. **服务器重新生成图片。** 上传的请求体就是图片本身（`Content-Type` 必须是 `image/jpeg` 或 `image/png`，别的类型在操作日志之前就拒绝，免得日志去解析图片内容；不超过 1 MB，受全局请求体上限约束）；服务器按内容判断格式，只接受 JPEG 和 PNG；先读尺寸，宽高超过 2048 的直接拒绝（不解码，防解压炸弹；浏览器端只会传 512×512），渐进式 JPEG 的扫描段超过 40 个也不解码（解码器每一段都要把整张图过一遍，段数不设限时 1 MB 的文件能算上几分钟）；整个进程同时最多解码 2 张，其余排队、等到请求时限就放弃；再解码、居中裁成正方形、缩放、透明部分铺白底，重新编码成 JPEG。存下来的是全新的图片：原文件里的 EXIF（含拍摄位置）、注释和夹带的内容都不会留下，伪装成图片的脚本也过不去。浏览器端先让本人裁剪（拖动、缩放）再上传，其他格式（WebP、GIF 等）由浏览器解码后转成 JPEG。
3. **内置头像**：壳里自带 12 个原创的几何图案头像（SVG，按名字引用）；选内置头像存成 `preset:<名字>`，后端按同一份名字表校验（两边的表由测试对齐）。上传的存成 `upload:<键>`，清除后为空（显示名字首字母）。`ga_user.avatar` 只会是这三种之一；迁移只留下名字完全对得上的内置头像和确实有图的上传头像，其余的值一律清空，外部地址不会显示。
4. **读取要登录。** 规范 §13.2 第 16 条要求公开接口只有登录相关的三条，所以头像不做成公开的图片地址：`GET /system/avatars/:key`（登录即可）返回 `data:image/jpeg;base64,...`，`?size=64` 取小图。键是随机的，只有看得到这个人资料的人（本人、数据范围内的管理员）才拿得到键；换头像或清除后旧键立刻失效；响应 `Cache-Control: no-store`（是别人的照片，不进浏览器磁盘缓存）。壳里新增 `GaAvatar` 组件按键取图并在内存里缓存，内置头像直接渲染，不发请求。
5. **本人自助**：`POST /system/avatar`（上传）、`PUT /system/avatar`（`{preset}` 选内置）、`DELETE /system/avatar`（清除），都是登录即可、只改调用者本人（路径里没有用户 ID；不放在 `/system/profile` 下，那里的三条接口保持不变），记操作日志 `profile.avatar`（上传的请求体只记成 `<image/jpeg, N bytes>`，不存图片）。`PUT /system/profile` 仍然不接受 `avatar` 字段（D-038 的规则不变）。
6. **没有头像时**显示账号（登录名）的首字母。配色从壳里定义的 100 组 [底色, 文字色] 里按账号固定挑一组（FNV-1a 散列取模：同一个人每次都一样，不同的人分散开）：20 个色系（红、橙、琥珀、黄、黄绿、浅绿、绿、青绿、青、天蓝、蓝、靛蓝、紫罗兰、紫、粉、玫红、棕，以及蓝灰、灰、暖灰三个灰色系）× 5 档深浅，在感知均匀的 OKLCH 色彩空间里取色；浅的几档配同色系的深色字，深的几档配白字；每组的对比度都不低于 4.5:1（WCAG AA），底色都不是黑色或白色，由测试检查。部署方先要白字，看过第一版后要求色系更多（灰色、浅绿、橙色），并同意文字颜色可以变，只要和底色区分明显。
7. **管理员只能清除**：`DELETE /system/users/:id/avatar`，要 `system:user:update`，受数据范围约束（范围外 404，D-039），非超管不能动超管账号（D-035），记操作日志 `user.avatar-clear`。管理员接口 `PUT /system/users/:id` 不再接受 `avatar`（传了也不改），用户管理表单里没有头像输入框。

理由：头像是每个人都想改的东西，但"上传文件"是后台里最常见的攻击入口之一（传脚本、传超大图、传带位置信息的照片、用外部地址追踪管理员）。只开一个用途单一、服务器重新生成内容、不落磁盘、要登录才能读的口子，能满足需求而不引入通用文件上传的风险；通用的文件上传和媒体库仍按 §1.3 留到以后单独设计。

## D-043 · 2026-09-29 · 并发交错与缓存回填：判断和写入放进同一把锁，缓存只在代数未变时回填

问题：凡是"先读、再据此写"的两步，在并发下都可能交错——读到的状态在写入之前已经被别人改掉。框架里这样的地方有：授权的重载（读库、换内存），改角色和删角色（读状态和引用数、再写），分配角色（核对角色、再写成员关系），几处进程内缓存的回填（读库、再写缓存）。同一条原则还要覆盖两处口径问题：用户表的排序规则忽略重音和大小写，登录名的别名（`ádmin` 查到 `admin`）要和限流、锁定的计数口径一致；字典同步拿着会话级锁的那条连接时，不能再从连接池里取第二条（`maxOpenConns: 1` 时会一直等）。

选择：
1. `Reload` 整个持锁（`reloadMu`），写入方都是先提交再重载，串行之后最后一次重载读到的一定是最新提交的状态（D-051 起重载整体发布一份快照）。
2. `UpdateRole`、`DeleteRole` 进 `WithSuperLock` 事务并锁角色行，锁内的状态和引用数都用锁定读（`lockRole` 返回 `FOR UPDATE` 读到的行、`FOR SHARE` 数引用）——锁定读看到的是最新已提交的数据，不受事务快照影响；分配角色（`AssignUserRoles`）也在这把锁里，并在锁内再核对一次每个角色仍然存在，三者互相串行。`lockRole` 在角色不存在时返回 `ErrRoleNotFound`，已删除的角色不再收授权、不留孤儿策略。改动授权后要重载内存策略，而重载用的是另一条连接，看不到调用方事务里未提交的写入，所以 `GrantRole`、`DeleteRole`、`Prune` 在外层事务里调用直接报 `ErrInTx`；字典 `Sync` 同理。
3. 字典、菜单缓存用缓存自己的失效代数：读库前 `Gen()`，读完 `SetIfGen`，判断和写入是缓存内部的一步。事务里读到的是事务快照，快照可能早于取代数的那一刻，所以事务里一律不回填。代数是整个缓存一个计数器，一次写入会让同时在读别的键的读方多查一次库，写入都是管理操作，可以接受。角色和成员关系不单独缓存，见 D-053。会话缓存命中时比一次到期时间。
4. 登录时查到的账号必须和归一化后的输入逐字相同，否则按"账号不存在"处理：不校验密码、响应和不存在的账号相同、失败记在输入的键上。这条规则在内核里，不依赖用户表的排序规则，自定义 `UserProvider` 一并覆盖；`UserProvider` 的契约据此写明（§4.1），要支持邮箱登录得先把邮箱解析成账号名。
5. 字典同步的全部 SQL 走拿锁的那条连接（`db.WithDB(ctx, conn)`），不再从池子里取第二条；用一个会克隆的会话操作那条连接，避免 Raw/Exec 留下的语句状态混进后面的事务。
6. 部署：一条测试保证 `main.go` 直接 import 的每个本仓库目录都在 `Dockerfile.server` 的 COPY 清单里（漏一个，镜像就构不出来）；nginx 示例把 `/readyz` 也反代给后端（否则落进单页应用回退，`index.html` 的 200 会被当成就绪）；镜像用 nginx 当前的稳定分支。
7. 前端：登出以服务端确认为准——只有服务端确认吊销、或会话确实已经结束，才算退出成功（D-044、D-052 细化）；工作台"上次登录"单独查一条，不在最近几条里找；数据中心、工作台的请求带序号，旧响应不覆盖新筛选。

理由：这些都是同一个模式——判断和依据判断的写入必须看到同一份已提交的状态，要么放进同一把锁并用锁定读，要么让缓存自己判断"读库期间有没有人写过"。用 `SetIfGen` 而不是"查代数再 Set"，是因为两步之间仍有窗口。登录别名放在内核里判断，是因为排序规则属于表、而限流的键属于内核，两边任何一边换了都不能让配额被拆开。测试：§13.2 第 62–64 条。

## D-044 · 2026-09-29 · 操作人的权限在锁内按库判断，内核不对外暴露 gorm 模型，排名按数据范围过滤

问题：D-043 让"目标对象的状态"在锁内按已提交的数据判断。操作人自己的权限同样是判断依据：非超管授权、分配角色、重新启用角色时要判断"自己有没有这个权限码、自己的范围有多宽"，这份依据不能来自内存（内存在写入提交之后才重载），也不能来自调用方事务在拿锁之前就建立的快照。同时定下几件相关的事：内核的表只能经过内核的服务读写；数据中心的活跃用户排名列出的是具体的人，要受数据范围约束；退出没得到服务端确认时怎么处理；以及几处界面细节。

选择：
1. `rbac.Service` 里非超管的这三类判断用锁内按库算出来的 `actorView`：操作人的启用角色、每个角色的策略（含通配规则，匹配规则和判定用的一样）和范围，全部用锁定读（`FOR SHARE`）——锁定读拿到的是最新已提交的行，不受事务快照影响，调用方的事务在拿锁之前做过读也没关系；锁内对目标角色的策略、范围和目标用户当前角色的读取同样用锁定读，`IsLastSuper` 也是。`GrantRole` 先拿超管锁再锁角色行，和改角色、分配角色、删角色互相串行。通配规则和未注册的权限码不算操作人"拥有"的：非超管不能把带这类规则的角色分配出去。请求级的判定见 D-051、D-053、D-054。
2. 内核公开包（`core/` 下 `core/internal` 之外）没有带 `TableName` 的导出类型：`rbac.Role` 只是数据结构，读写库用包内的 `roleRow`（同一份字段），`userRole`、`policyRule`、`roleDataScope` 不导出；一条测试扫 `core/` 的源码，保证以后也不会有。
3. 活跃用户排名按操作人在用户资源上"查看用户"的范围过滤：全部范围看整个端，部门范围只看范围内的用户，仅本人（包括没有查看用户权限的）只看自己；内核提供 `oplog.TopUsersIn`（范围内的用户作为子查询交给数据库，D-055），和会话列表的 `ListSessionsIn` 一个路数。
4. 退出没得到服务端确认时记一个按端区分的"待补退出"标记（发请求之前就写，请求在途时关掉页面也算），下次启动先补做退出而不是恢复会话，补做成功才清；登录成功后作废。标记的内容和清理规则见 D-049、D-051。提示是"下次打开本站时会先补做退出"。
5. 其余：头像预览用 `FileReader` 的 `data:` 地址（部署示例的 CSP 只放行 `img-src 'self' data:`）；工作台"上次登录"按会话 ID 找本次登录的日志，再往前找一条成功的；"下线其他设备"是内核的一条语句（`auth.Service.RevokeOtherSessions`，返回吊销数），会话再多也没有边界；安全监控缓存按端单飞——过期时只让一个请求查库、其余等它，查库失败时排在后面的一起失败，前端两类请求各自只认最后发出的那次。

理由：第 1 条是 D-043 的同一原则再往前推一步——不只是目标对象的状态，操作人自己的权限也属于"判断依据"，必须在锁内看已提交的状态；用锁定读而不是要求调用方把锁放在事务最前面，是因为后者靠约定、前者靠数据库保证。第 2 条让内核的表只能经过内核的服务读写：公开类型只是数据结构，不带 `TableName`。测试：§13.2 第 65–67 条。

## D-045 · 2026-09-30 · 操作人的超管身份在锁内按库认定，改密与重置排队

问题：`Principal.Super` 是请求认证时得出的结论，整个请求里不变。超管能跳过的检查最多，锁内的判断如果沿用它，认证之后才提交的降级在这个请求里就不起作用。同样要在锁内按已提交状态判断的还有：本人改密和管理员重置密码谁先谁后；挪部门、选部门负责人时用到的数据范围。另外定下几处前端的可靠性细节。

选择：
1. **超管身份在锁内重读。** `rbac.Service.CurrentActor` 在超管锁里用锁定读看操作人当前是否仍有启用的超管角色、账号是否仍启用，返回 `Super` 更新过的身份；锁内判断操作人权限用的 `actorView` 也不从 `actor.Super` 起算。分配角色、改角色、授权、重置密码、改用户资料和部门、启停账号、清除头像、让会话下线，都在锁内先认定，之后的判断只用新身份（D-047 起统一由 `WithActor` 完成）。账号被停用的在途请求不再有任何权限。服务器命令行的身份（没有用户 ID）由调用方给出。
2. **改密和重置排队。** 本人改密在事务里锁住自己的账号行和会话行，确认会话仍然有效、密码仍是刚才验证的那个，才写新密码：会话已被吊销回 401，密码已被改过按旧密码错误处理。加锁顺序和核对方式见 D-046、D-047。`UserProvider` 接口不变。
3. **挪部门、选负责人按库算范围。** `rbac.Service.DataFilterLocked` 和 `DataFilter` 一样，但在锁内按已提交的授权算；改部门、建部门都先拿超管锁再锁部门表，负责人的检查在事务里，并对负责人行加共享锁。建用户整个在超管锁里，加锁顺序统一为"超管锁 → 部门 / 用户"，不会互相等待。
4. **退出标记兜底。** 写不进 `localStorage` 时退而写一个 `SameSite=Strict` 的 Cookie（名字见 D-059），读、清两处都看。
5. **其余。** 数据中心的文字按正在显示的数据的区间写，换区间时整页显示加载态，失败时区间按钮退回；服务器指标和安全态势的请求各自最多一个在途，上一次没回来就跳过这一轮；"上次登录"取到本次这一毫秒为止的几条，跳过本次和它之后的。

理由：D-043、D-044 的原则再往前推一步——锁内的判断不只要看目标对象和操作人权限的已提交状态，操作人的身份本身也是判断依据。超管可以跳过的检查最多，沿用旧身份的代价也最大。测试：§13.2 第 68–70 条；§13.2 第 15 条的并发用例里，被拒的一方按锁内重新认定后的身份处理，"恰好一个成功、始终至少剩一个可用超管"不变。

## D-046 · 2026-09-30 · 在途请求跟着身份走：停用和吊销让在途写入作废，换了人的请求不重放，改密与重置同一加锁顺序

问题：一个写请求从认证到执行之间有一段时间。这段时间里账号可能被停用、会话可能被吊销，同一个浏览器页面也可能已经退出、换了别人登录；请求最终以谁的身份执行、还执不执行，要有明确的规则。另外，本人改密和管理员重置密码、停用账号会锁同样的两行（用户行、会话行），加锁顺序要统一。界面上，几处对话框和列表要防止慢响应覆盖新状态。

选择：
1. **锁内认定操作人时一并确认账号和会话。** 账号已停用或不存在、会话已吊销或过期的，`CurrentActor`（以及锁内判断用的操作人视图）直接回 401，整个请求作废、什么都不写。会话状态由 `rbac.Options.SessionActive` 提供（`core/app` 接上会话表的普通读，不走状态缓存）。都是普通读：调用方先拿超管锁，锁后第一次普通读建立的快照包含拿锁时已提交的停用和吊销；不用锁定读，免得和改密、吊销会话的加锁顺序交叉。
2. **换了人的请求不重放。** 认证状态里有"登录身份的代数"：登录、退出、登录失效时变，刷新令牌不变。请求发出时记下它，收到 401 时代数已经变了就不刷新、不重放、不提示。请求层的 `TokenStore` 有可选的 `epoch()`。D-047、D-052 把这条推广到所有结果和请求发起的时刻。
3. **改密与重置同一加锁顺序。** 本人改密和重置密码、停用账号一样，先锁用户行、再锁会话行（"用户行 → 会话行"）；会话无效就整体回滚。密码哈希的核对见 D-047。
4. **界面。** 角色授权对话框打开时先清空表单，读完之前保存按钮不可用，前一次打开的慢响应作废；调查时间线换查询对象时先清空列表和游标，旧的响应（包括"查看更多"）不再处理；错误日志详情只认最后一次打开的；待补退出标记同时写 localStorage 和 Cookie。

理由：在途请求的身份应当以它真正执行的那一刻为准。凡是在超管锁里执行的写操作，锁内都重新确认"这个人此刻还是不是这个人、还有没有这个身份"；锁外的读取以请求入口为准。测试：§13.2 第 71 条；§13.2 第 15 条的并发用例里，被停用的一方回 1004。

## D-047 · 2026-09-30 · "拿锁"和"重新认定操作人"合成一个入口，登录和改密在锁住账号行的事务里核对密码，前端作废换了人之前的一切结果

问题："在途请求的身份以执行时为准"（D-045、D-046）如果靠每条写路径自己决定在哪一步拿锁、在哪一步重新认定，漏一步规则就不成立，新加的写接口也容易忘。同样的"校验之后、写入之前"的间隔还出现在登录（校验密码、再建会话）和改密（验证旧密码、再写新密码）上：两步之间密码可能被重置、账号可能被停用，同一个会话也可能有另一个改密请求先提交。前端同理：登录身份代数如果只在 401 分支里看，换了人之前发出的刷新、`/auth/me`，以及遇到的 1006、2002，仍会作用到现在登录的人身上。

选择：
1. **后端写操作只有一个入口。** `rbac.Service.WithActor(ctx, actor, fn)` 拿超管锁、按库重新认定操作人（账号、会话、角色、权限、范围），再把认定后的操作人交给 `fn`；`fn` 里的权限判断用新增的 `AllowedLocked`，数据范围用 `DataFilterLocked`，不再用请求上的 `actor`。系统模块的写接口全部改走它（用户、部门、岗位、字典、会话、头像）；角色的写操作在 `rbac` 内部，建角色走 `WithActor`，其余在同一把锁里调用同一套认定；菜单的写操作走 `WithActor`，顺序固定为"菜单互斥锁 → 超管锁"。§13.2 第 72 条按路由表遍历：平台端每一条需要权限码或超管的写路由都必须有用例，用例和路由表双向核对，新加的写路由不补用例测试就失败。
2. **登录和改密在锁住账号行的事务里核对密码。** `portal` 新增可选接口 `UserLocker`（`LockByID`，加排他锁读账号），`modules/system` 的用户来源实现它。登录：密码仍在事务外校验（bcrypt 慢，不能拿着行锁算），建会话的事务里先锁账号行，确认密码哈希和状态没变再建会话；变了就按密码错误或账号停用失败，计入失败次数。本人改密：先锁账号行、再锁自己的会话行（和重置、停用一样是"用户行 → 会话行"），会话无效回 401，密码哈希已经不是刚才验证的那个回 3001"旧密码不对"，然后才写。没加进 `UserProvider` 本身，是为了不让已有的自定义用户来源编译失败；没实现 `UserLocker` 的退回事务里的普通读，只有尽力而为的保证，规范 §5.7 写明。
3. **前端作废换了人之前的一切结果。** 请求发出时记下代数，结果回来时代数变了，成功或失败一律按新的前端错误码 `Superseded`（-2）失败：不交数据、不刷新、不重放、不触发锁屏和改密跳转、不提示。刷新发出时也记代数，回来时变了就不写令牌；刷新失败而这期间换了人的，不清现在的登录、不通知登录失效。单飞刷新可能是上一个人发起的：现在这个人的请求碰上它作废，就自己再刷新一次。登录失效时先通知 `onAuthLost` 再清。启动恢复登录态在途时用户登录了的，恢复失败不清这次登录。调查时间线回到没有查询条件的地址时清空结果、作废在途的查询。

理由：同一类问题要在一个地方解决。后端把"拿锁"和"重新认定"合成一个函数，业务代码拿到的只有认定后的操作人，没有机会用错；再用按路由表遍历的测试兜底，覆盖不依赖逐条想到。登录和改密的"校验"和"据此写入"之间，要在写入的事务里重新核对校验时依据的数据。前端把代数检查放在请求和刷新的出口，而不是某个分支里。测试：§13.2 第 72–74 条。

## D-048 · 2026-09-30 · 刷新绑定会话、迟到的退出不影响新登录、本人写操作和路由权限也在锁内复核

问题：同一浏览器的标签页共用一个刷新 Cookie，登录身份却在各自的内存里：一个标签页换了人登录，另一个标签页并不知道。刷新、退出这两个会动 Cookie 的动作要知道自己针对的是哪个会话，响应迟到时也不能作用到新登录的人身上。另外，只需登录的本人写操作、写后回显、路由守卫要求的权限码，也要按 D-047 的入口在锁内复核；身份变了时标签栏要跟着清空。

选择：
1. **刷新绑定会话。** 登录、刷新的出参加 `sessionId`，前端认证状态记下它；刷新时放进请求头 `X-GA-Session`。服务端发现 Cookie 里不是这个会话就回 401，不轮换、不改 Cookie（那是另一个标签页的登录），这个标签页按登录失效回登录页。页面刚打开、还不知道自己是谁时不带这个头，按 Cookie 恢复。响应里的 `Set-Cookie` 由浏览器处理、前端拦不住；有了绑定，最坏的结果是标签页发现 Cookie 不属于自己的会话、需要重新登录，而不会以别人的身份继续。
2. **迟到的退出不影响新登录。** 前端退出在途时登录身份变了的，迟到的退出不清认证状态、不重写退出标记。服务端对刷新 Cookie 的处理见 D-049（服务端从不删除它）。
3. **本人写操作也走 `WithActor`**，§13.2 第 72 条的路由遍历扩到只需登录的写路由（认证接口本身除外），用例表同样双向核对。
4. **回显用锁内认定后的身份。** 查看范围在写操作的锁里用 `DataFilterLocked` 算好，提交后按它决定回不回完整资料。
5. **身份一变就清标签栏。** 布局状态监听登录身份代数，不再靠每个退出入口各自调用。
6. **锁内复核路由权限码。** `Require`、`RequireSuper` 中间件把本次路由的要求放进请求上下文；锁内认定操作人（`WithActor`、`AllowedLocked`、`DataFilterLocked` 以及 `rbac` 内部的角色写操作都经过同一处）时按已提交的授权再核一遍，不满足回 403。走锁的写操作以拿到锁那一刻为准，锁外的读取以请求入口为准。

理由：服务端能认出"这个 Cookie 不是这个标签页的会话"，前端做不到；把绑定放在服务端，多标签页换人只会让旧标签页掉线，不会串号。其余几条是把同一规则用到本人写操作、回显和路由权限上，并放在唯一的入口里（锁内认定、身份代数），而不是每个调用方各记一遍。测试：§13.2 第 75–78 条和第 72 条。

## D-049 · 2026-09-30 · 对不上的刷新凭证不吊销会话、服务端从不删除刷新 Cookie、待补退出绑定会话、409 按间隔重试

问题：刷新接口不需要访问令牌，只凭 Cookie；Cookie 里的会话号也会出现在会话列表和各类日志里。"刷新凭证和会话对不上"时怎么处理、哪些动作能让一个会话下线，要定清楚：让会话下线只应属于 `system:session:revoke`。另外几处是多标签页共享一个 Cookie 带来的时序问题：响应迟到时浏览器仍会执行里面的 Cookie 指令；"待补退出"的标记要知道针对的是哪个会话；同一会话在两个标签页同时刷新时，后到的一方会先拿到 409。

选择：
1. **凭证和会话对不上只拒绝、不吊销。** 只有"上一个凭证在宽限期之外重放"才算泄露——拿它的人确实持有过有效凭证；这时照旧吊销整个会话并记 `refresh_reuse`。两者都对不上的回 401、会话不动、Cookie 不动，记新的警告级安全事件 `refresh_mismatch`（带会话和用户，说明写清会话未吊销）。代价：比一次轮换更旧的凭证副本被重放时只有告警、没有自动吊销；换来的是"让会话下线"只属于 `system:session:revoke`。会话表不加历史列：一次轮换的窗口覆盖了偷到 Cookie 后马上用的情形，更老的副本靠告警。
2. **服务端从不删除刷新 Cookie。** 只在登录和轮换成功时写它；退出、失败的刷新、解锁次数用完都不再下发"删除 Cookie"。吊销过的会话的 Cookie 留在浏览器里没有用处：下次刷新回 401，下次登录会换掉它。迟到的响应只可能带着一个成功轮换的 Cookie，最坏是需要重新登录（D-048）。
3. **待补退出的标记绑定会话号。** 标记的值是那次要退出的会话号（localStorage 和 Cookie 各一份）。启动时先照常刷新：换来的正是这个会话，才补做退出、不恢复；换来的是别的会话，说明这个浏览器已经没有那个会话的凭据，标记作废、照常恢复；刷新被服务端拒绝同样作废，网络故障才保留。不知道会话号时不写标记，不带会话号的标记被忽略并清掉。
4. **409 按间隔重试，重试用尽不算登录失效。** 默认 200、500、1000、2000 毫秒四次，累计约 3.7 秒，远在 10 秒宽限期内；用尽仍是 409 只让这次请求失败，登录状态留着，登出遇到它也不算服务端确认。同源的标签页之间用 Web Locks（`ga.refresh:<接口前缀>`）把刷新串起来，轮到时浏览器里已经是新 Cookie；拿不到 Web Locks（不安全的上下文、旧浏览器、测试环境）或等锁超过 5 秒时直接刷新，仍有重试兜底。

理由：第 1 条是原则问题——一个动作需要什么权限，不能因为走的是刷新接口就变成不需要；"对不上"证明不了任何人的凭证泄露，据此吊销就是把撤销权限送给了所有能看到会话号的人。第 2 条把"哪个 Cookie 该删"这个服务端回答不了的问题整个去掉：服务端不删，就没有迟到的删除。第 3、4 条都是多标签页共享一个 Cookie 带来的时序问题，解法是让前端知道"这次操作是针对哪个会话"、"这次失败是不是暂时的"。测试：§13.2 第 79–80 条。

## D-050 · 2026-09-30 · 刷新先查账号再轮换、错误日志按端隔离、按标签页记会话号

问题：几处"失败到底意味着什么"要区分清楚：标签页重载后要记得自己绑定的会话，否则会按浏览器里最新的 Cookie 恢复成另一个标签页登录的账号；跨标签页刷新锁"等锁超时"和"锁内的刷新本身慢"是两回事；刷新时数据库临时出错和账号已停用是两回事；前端的断网、5xx 和服务端明确拒绝也不能等同。另外，错误日志要和其他审计列表一样按端隔离。

选择：
1. **按标签页记会话号。** 登录和刷新成功时把会话号写进 `sessionStorage`（按标签页、重载后还在），清除登录状态时删掉；启动刷新先读它、带上 `X-GA-Session`。服务端拒绝时带翻译键 `auth.sessionSwitched`，登录页据此说明"这个浏览器已在另一个标签页登录了别的账号"；这份记录同时被清掉，用户看过提示之后再重载，就按 Cookie 恢复成那个账号——那是他的选择。
2. **拿到锁就停掉计时。** 只有真的没拿到锁才在锁外直接刷新。
3. **刷新先查账号再轮换。** 查会话属于谁、查账号，数据库临时出错回 503，会话和凭证都不动；账号不存在或停用照旧轮换后吊销。前端只在刷新被服务端明确拒绝（401）时当作登录失效，断网、超时、5xx 只让这次请求失败。
4. **错误日志按端隔离。** 没登录的请求按路由模板（`/api/<端>/v1/...`）归到端；列表只看本端和不属于任何端的，详情属于别的端时回 404。`audit.ErrorFilter` 加了 `Portal`、`IncludeGlobal`，和安全事件的过滤一致。已经写进库里、端为空的旧记录按"不属于任何端"处理。

理由：都是时序问题：让失败的判断只依据确定的事实——服务端明确拒绝才算登录失效、真的没拿到锁才绕开锁、真的查到账号停用才吊销。错误日志和其他审计列表一样按端隔离。测试：§13.2 第 81–83 条。

## D-051 · 2026-09-30 · 授权快照整体发布、重载失败不按旧快照判定、登录防跨站、详情返回检查过的那一行

问题：授权数据（权限码策略、数据范围）先提交到库、再重载到内存。分几步换上时，判定方可能拿到一新一旧；重载失败时内存里还是旧的，而旧的可能比库里宽。登录接口和刷新、退出一样会改浏览器状态（写 Cookie），要同样校验请求来源。按范围读详情时，检查范围用的那一行和返回给调用者的那一行要是同一行。前端对"临时故障"和"服务端拒绝"也要分开处理绑定的会话号和待补退出标记。

选择：
1. **授权快照整体发布。** 权限码策略和数据范围在一个只读、可重复读的事务里读（新增 `db.Snapshot`），建好新的判定器和范围表后一次换上；一次判定只取一份快照。重载失败时标记"过期"：之后的判定先重试重载（最多每秒一次，别的重载正在进行时不等），仍失败就回 503。不拿旧快照判定——它可能比库里宽；也不退到"没存范围取默认值"——默认值可能比存下来的宽。
2. **登录和刷新、退出一样防跨站。** 要求 `X-GA-Client: web`、Origin 在白名单、`Content-Type: application/json`，在算密码、建会话之前检查，被拒的不记登录尝试（否则跨站页面能借受害者的 IP 刷失败次数）。表单设不了自定义头；跨站的 fetch 带自定义头或 JSON 类型要先过预检，而服务端不开 CORS。前端登录请求带上这个头。
3. **检查的那一行就是返回的那一行。** 用户详情和写后回显在一个只读快照事务里读账号、角色、部门、岗位，用检查过范围的那一行拼资料，不再按 ID 重读。
4. **只有服务端明确拒绝才删标签页会话号。** 启动时的断网、超时、5xx 只清这一页的登录态，会话号留着，下次重载照样带上；服务端回 401（登录失效，或提示过换了账号）才删。
5. **待补退出按会话号各自保存、各自删除。** 标记是一组会话号（`localStorage` 和 Cookie 各一份，取并集，最多 8 条）。退出只删自己那条；启动时刷新换来的正是其中一条才补做，换来别的会话就删掉读到的那些；刷新因 Cookie 不能用被拒才删读到的那些，因 Cookie 属于别的会话被拒时不删；登录只删登录前就在的。两个标签页恰好同时改标记时仍可能丢一次更新（`localStorage` 没有跨标签页的原子操作），最坏是少补做一次退出，会话照常到期。

理由：授权收窄必须"要么生效、要么拒绝"，不能在两者之间用旧的宽状态继续放行；判定和返回的数据都要来自同一个时刻的状态。登录写 Cookie，和刷新一样是会改浏览器状态的公开接口，要同样防跨站。前端只依据确定的事实删绑定和标记。测试：§13.2 第 84–87 条。

## D-052 · 2026-09-30 · 身份在发起时绑定、按范围取 ID 和读数据用同一个快照、退出确认只认"会话已结束"

问题：请求和刷新的登录身份应当在发起时绑定，而不是在真正发送的那一刻去读"现在是谁"：请求层的拦截器异步执行、跨标签页的刷新要等锁，等待期间这一页可能已经退出或换了人。按范围读列表时，"范围内有哪些人"和"这些人的数据"要来自同一时刻。退出是否已被服务端确认，也只能依据服务端明确给出的事实。

选择：
1. **请求和刷新在发起时绑定身份。** 请求进入请求层时取下代数和访问令牌，发送时用这个令牌；包一层适配器，真正交给网络之前再核对代数，变了就作废、不发出去；401 后的重放沿用第一次的代数。刷新在发起时记下代数和会话号，拿到锁、每次重试发出、写回令牌之前都核对。同一身份内的刷新和重试照常。
2. **范围和数据在同一个只读快照里读。** 会话列表（范围、ID、会话、账号名、角色）、活跃用户排名（范围、ID、操作次数）、用户列表（范围、用户行、角色、部门、岗位，本来就是一条带范围的查询，顺带让同一页的资料来自同一时刻）都放进 `db.Snapshot`。返回的是取范围那一刻的数据，不是把不同时刻的拼在一起。
3. **服务端说清楚会话是不是已经结束。** 刷新失败时，会话不存在、已吊销、已过期，或这次因重放、账号停用刚被吊销，401 带翻译键 `auth.sessionEnded`；其他 401 不带。前端退出只在登出成功或刷新带这个键时算确认，否则待补退出的记录留着、提示用户退出没被确认。"这个浏览器已经没有那个会话的凭据、补不了"仍按 D-049 在启动时清理，但那不再被说成"退出已确认"。

理由：身份要跟着请求走，而不是在发送那一刻去读"现在是谁"；判定和返回的数据要来自同一个时刻；"服务端确认"只能来自服务端明确说出的事实。测试：§13.2 第 88–90 条。

## D-053 · 2026-09-30 · 成员关系和角色状态进授权快照、解锁在锁内复核密码、吊销失败不说会话已结束、认证动作核对身份

问题：一次权限判定要用到成员关系（谁有哪些角色）、角色状态和角色的权限码。这几样如果分别读取、分别缓存，就可能拼出一个在任何时刻都不存在的组合。另外：前端的认证动作（`/auth/me`、登录、锁屏、解锁、改密）在每次等待之后都要核对身份；解锁核对密码和解除锁定之间要排除并发的改密；刷新时吊销会话没写成，不能告诉前端会话已结束。

选择：
1. **成员关系和角色状态进授权快照。** 快照里是全部角色（ID、端、是否超管、状态）、全部成员关系、权限码、范围，在同一个只读快照事务里读、一次换上；判定只查快照，不再有单独的角色缓存（D-043 的"读方不回填旧值"随之不需要了，由"提交之后立即重新发布"保证撤销立即生效）。分配、撤销角色和启停角色在提交之后重新发布（`db.AfterCommit`），授权、删角色照旧。快照超过有效期（默认 15 秒，和以前角色缓存一样）时下一次判定先重读，兜住命令行之类进程外的改动。代价：每次改成员关系都重读全部成员关系，规模是"用户 × 角色"的行数，后台管理的量级可以接受。
2. **认证动作在每次等待之后核对身份。** 记下开始时的代数，等待之后、写状态或发下一步请求之前核对，变了就以 `Superseded` 作废；登录页、锁屏、改密页遇到它不提示。启动恢复的刷新回来时已经换了人，就不再补做退出、拉 `/auth/me`。
3. **解锁在锁内复核密码。** 核对密码之后，在一个事务里先锁账号行、确认密码哈希没变，再解除会话锁定——和本人改密、重置密码同一个加锁顺序（用户行 → 会话行）。密码变了按输错处理。
4. **吊销没写成就不说会话已结束。** 账号停用分支吊销失败（会话已不存在除外）回 503。

理由：一次判定用到的全部授权数据必须来自同一个时刻；前端只把确定属于当前身份的结果写进状态；"会话已结束"和"密码仍有效"都要以锁内、已提交的事实为准。测试：§13.2 第 90–93 条。

## D-054 · 2026-09-30 · 数据范围按请求的数据库视图算、SQL 日志不带参数

问题：数据范围由两类输入算出：授权（角色、权限码、存下来的范围）和组织（操作人所在的部门、下级部门）。两类输入要和被判断的数据来自同一个数据库视图，否则可能把两个时刻的状态拼在一起。另外，规范 §5.6 要求密码及其哈希不进日志，而 gorm 在出错和慢查询时默认把绑定参数填进 SQL 交给日志。

选择：
1. **数据范围按请求所在的数据库视图读。** `DataScopeOf`、`DataFilter` 读操作人的角色、角色状态、权限码、范围、部门和下级部门，全部用 ctx 里的数据库视图（普通读，不加锁），并自己包一层 `db.Snapshot`：调用方已经在只读快照里时，和它读数据是同一个视图；不在时至少这几项是同一时刻的。系统模块里所有按范围读的地方（用户列表、详情、下拉、会话列表、活跃用户排名、写后回显）都把"算过滤条件"和"读数据"放进同一个快照。授权快照里去掉了范围，只留权限码判定要用的角色、成员关系、策略。代价：每次按范围读多几条小查询（操作人的角色、每个角色的策略和范围）。
2. **SQL 日志只记模板。** SQL 日志实现 gorm 的 `ParamsFilter`，只返回占位符模板。gorm 的 `Scan` 走它自己的记录器、参数在到达我们之前已经被展开，所以模板打上标记，没有标记的 SQL 不记文本，改记调用位置（文件和行号）。数据库驱动的错误文本（如唯一键冲突）可能带着冲突的值，那是登录名、编码这类本来就不保密的列，不另外处理。

理由：判断数据可不可见用的每一样输入，要和被判断的数据是同一个时刻的；日志是另一条会被复制、长期保留的出口，凭据材料不能经它流出。测试：§13.2 第 94–95 条。

## D-055 · 2026-09-30 · 撤权到发布之间判定先等、部门负责人按用户范围遮蔽、改密与验证码限流、容量上限、门禁在工具出错时失败

问题：
- 改授权的事务提交之后才重新发布内存快照，提交到发布之间的判定要有规则。
- 部门列表里的负责人是具体的人，要和用户资料一样受"查看用户"的范围约束（D-039 第 6 条约束的是设置负责人的人）。
- 本人改密要核对旧密码，每次一次 bcrypt，需要次数上限；公开的验证码接口每次画图编码，需要速率和并发上限。
- 几处输入规模需要上限：按范围列会话和排名时的用户集合、字典项的数量和层数、页码。
- 前端：没有令牌的请求收到 401 时，不应靠浏览器里的 Cookie 自动恢复登录态。
- 门禁脚本在底层工具出错时必须失败，不能对着空结果报 OK；许可证检查只认许可证正文。

选择：
1. **"待发布"标记。** 改授权的写入（授权、分配或撤销角色、启停角色、删角色、清理策略）在事务里写完、提交之前标记"待发布"，事务结束后提交了就重新发布，然后撤掉标记；回滚（包括 panic）也撤掉。标记在的时候，权限码判定先等（最多 3 秒，超时回 503）。新增 `db.AfterEnd`：事务结束后不论提交还是回滚都调用。代价：改授权的那一小段时间里判定要等几毫秒。
2. **负责人按用户范围遮蔽。** 部门列表和改部门的回显，负责人不在调用者"查看用户"范围内时不给 ID 和名字，标记 `leaderHidden`；范围、部门、负责人在同一个只读快照里读。改部门的请求里 `leaderUserId` 是可选的：不给就保持原来的负责人（调用者可能看不到他是谁），给 0 才清空；前端编辑这样的部门时显示"保持原负责人"，另有"清除负责人"。
3. **限流。** 本人改密：同一会话 15 分钟内最多核对 5 次旧密码，先占次数再做 bcrypt，成功清零，用完回 429 并记安全事件 `pwd_change_throttled`。不套用登录的失败锁定——那样别人能把账号主人锁在改密之外。验证码：同一来源 IP 每分钟 30 张，同时最多画 8 张，满了直接拒绝。两者用新的内部包 `ratelimit`（按键的固定窗口计数，键数有上限；不排队的并发闸门）。
4. **容量上限。** 会话列表、活跃用户排名的"范围内的用户"作为子查询交给数据库（`auth.Service.ListSessionsIn`、`oplog.TopUsersIn`）。一本字典最多 1000 项、5 层，后台加项和代码声明都检查；库里更深的历史数据拼树到 5 层为止。页码上限 5000（`httpx.MaxPage`）。
5. **无令牌的请求不自动刷新。** 请求发出时没有令牌，说明这一页此刻没有登录身份；收到 401 就是 401。恢复登录态只走启动时显式的刷新。
6. **门禁在工具出错时失败。** 先把 `go list`、`find`、`git log` 的输出完整取出来再检查，失败就退出；`grep` 区分"没命中"和"出错"；`gofmt -l` 失败时 fmt-check 失败。新增 `scripts/test-gates.sh`（`make gates-test`，进 `make ci`）：用会失败的假 go、假 gofmt 和写错的词表验证四个门禁都会失败。许可证检查只认许可证正文（LICENSE、COPYING、UNLICENSE），NOTICE、PATENTS 照样收录但不算；前端读不了已打包的包的 package.json 时构建失败。

理由：撤权要么已经生效、要么判定在等它生效，不能在两者之间按旧状态放行；具体是哪个人要按用户范围来，部门信息本身可以公开；会做昂贵计算的入口都要有上限；门禁报 OK 的前提是它真的检查过。测试：§13.2 第 96–100 条；门禁自测（`make gates-test`）用会出错的假工具和写错的词表验证每个门禁都会失败。

## D-056 · 2026-10-01 · 部门写后回显按库认定超管、代码字典层数边界、登录防护计数有键数上限

问题：
- 部门的写后回显要和用户的写后回显（D-054）同一规则：按写入时认定的身份算范围，不沿用请求开始时的超管标记。
- 代码声明的字典和后台加项、拼树，对"5 层"的算法要一致。
- 登录防护按 IP、账号、"账号 + IP"计数和锁定，状态在进程内存里，需要键数上限。

选择：
1. **部门回显和用户回显同一规则。** 真实登录用户的回显不沿用传进来的超管标记，在回显自己的只读快照里按库算角色、范围、部门和负责人；提交后、回显前再被收窄也照样按收窄后的算。服务器上的命令（UserID 为 0）没有角色可重读，照调用方给的算。
2. **没有下一层就不算一层。** 声明校验遇到空的下级直接返回；超过 5 层照样拒绝。补上"正好 5 层、正好 1000 项合法"的断言。
3. **登录防护计数有键数上限（默认 30 万，限流记录和失败记录合计）。** 满了不接纳新来源：这次尝试要新建的记录放不下时按限流回 429（记 `login_rate_limited`），已有来源照常计数。已有的失败次数和锁定一个都不逐出——逐出活跃的键等于替攻击者清掉失败次数和锁定。准入的规则见 D-057。表满时先提前清一次过期数据，两次提前清理至少隔 10 秒，避免表满时每个请求都遍历一遍全表。代价：遭到大规模分布式登录攻击、表满的那一两分钟里，没有登录过的新来源要等过期数据清掉才能登录。

理由：写后回显跟着写入时认定的身份走，不能比写入本身更宽；同一个上限在各个入口要一致；进程内的防护状态必须有界，容量满时宁可拒绝新来源，也不能丢掉已有的失败记录和锁定。测试：§13.2 第 101–102 条，字典声明的边界见第 99 条。

## D-057 · 2026-10-01 · 登录防护的键数上限是硬上限

问题：D-056 的上限要成为硬上限，每个会新建键的地方——登录的限流记录、失败记录、锁定，以及锁屏解锁输错时的失败记录——都要受同一个预算约束，而不是先接纳、事后再记。

选择：
1. **键只在准入时新建。** 登录（`Check`）被接纳时，把这次尝试可能用到的键——IP 和账号两个限流键、"账号 + IP"和账号两条失败记录——一次建好；放不下（先提前清一次过期数据）就按限流回 429，一个键都不建。
2. **锁定并进失败记录。** 锁定截止时间是失败记录上的一个字段，不再单独占键；记失败、加锁只改已有的记录。
3. **在途尝试钉住它的记录。** 被接纳的尝试（`Attempt`）结束前（`Fail`、`Succeed`、`Done`，登录处理里 defer `Done`），它的两条失败记录不会被过期清理、管理员解锁删掉；结束时没有内容的记录顺手删掉。
4. **解锁走同一套准入。** 锁屏解锁先 `Admit`（只预留失败记录，不计登录限流），放不下时在占用解锁次数、核对密码之前回 429。

这样键数任何时刻都不超过上限，已有的失败次数和锁定仍然一个都不逐出。代价：一次被接纳的尝试即使最后成功，也临时占着两条失败记录；表满时，从没失败过的"账号 + IP"组合也要等过期数据清掉。

理由：容量上限只有在每个新建键的地方都受同一个预算约束时才是上限；在核对密码之前拒绝，比核对完再决定记不记失败安全——失败记录不能丢。测试：§13.2 第 103 条（含随机交错下的不变量）。

## D-058 · 2026-10-01 · 审计落库、登录细节、交出权限的统一规则与部署默认值

问题：这一条集中定下一组细节规则：
- 审计记录的部分字段来自请求方（User-Agent、路径、登录名），可能含非法 UTF-8 或被截断的多字节字符，严格模式的 MySQL 会整行拒绝；审计记录不能因此丢失。
- 登录失败的响应和耗时不能透露账号是否存在，包括超长密码、账号没有密码这些边角情况；被遮蔽的部门负责人也不能靠反复提交试出来。
- 代码字典里已经不在声明中的遗留项，值仍归代码。
- "交出权限"的操作（分配角色、重新启用角色、重新启用账号）用同一套检查。
- 只需登录的本人写操作不占用全端共用的锁。
- 便宜的拒绝（被限流、被锁定的登录）不每次写库；IPv6 的限流粒度；密码核对的 CPU 上限。
- 刷新 Cookie 只接受本主机写入。
- 部署示例和镜像的默认值、新增模块指南的写法、几处输入上限。

选择：
1. **审计字符串入库前整理。** 新内部包 `textx.Clip`：非法 UTF-8 换成 U+FFFD，在字符边界截断到字节上限；会话、登录日志、操作日志、错误日志、安全事件的截断都走它。合并写库遇到"这一行本身写不进去"的错误（`db.IsDataError`：1048、1264、1265、1292、1366、1406）直接丢弃这一批次数、记一行日志，不放回去；连接断开这类可重试的错误照旧放回去。密码已核对、会话没建成时记登录日志（原因 `error`）。
2. **超长密码照样比较。** `Verify` 遇到超过 72 字节或账号没有密码，先做一次和"账号不存在"相同的假比较再返回失败。
3. **明确给出的原负责人也要在范围内。** 只有不给 `leaderUserId` 才是"保持原负责人"（不做检查）；给出的 ID 等于原负责人时照样查"查看用户"的范围，范围外和不存在回同一个错误。范围内的原负责人停用了仍可保留。
4. **遗留项归代码。** 代码字典的项（包括遗留项）一律不能改值；遗留项不能改成启用（`dict.legacyItem`），不给状态时保持停用；读的时候代码字典里没锁定的项一律按停用算（`Has` 为假、读接口 `status` 为 0），库里被改成了启用也不认。前端编辑遗留项时值和状态都是只读的。
5. **重新启用账号按分配规则。** 新增 `rbac.Service.CheckEnableUser`：非超管把停用的账号改成启用时，账号当前启用的角色要都是他能分配的（和分配角色同一套检查：敏感权限码、自己没有的权限码、更宽的范围）。停用不受这条限制。
6. **本人写操作只锁本人。** 新增 `rbac.Service.WithSelf`：事务里锁本人的账号行（`portal.UserLocker`），确认账号启用、会话有效再执行；个人资料、头像、下线其他设备用它。停用、改密、重置都先锁账号行，顺序一致；和吊销会话的先后见 D-059。
7. **便宜的拒绝不写登录日志。** 被限流、被锁定的登录只记安全事件（按来源一分钟合并、次数不丢），登录日志只记核对过密码的尝试。
8. **IPv6 按 /64，密码核对有并发上限。** 限流和"账号 + IP"计数的 IP 键：IPv4 按地址，IPv6 按 /64（`ratelimit.IPKey`）；验证码限流同样。登录、解锁、本人改密共用一道不排队的闸门（按 CPU 数，至少 8），满了回 429，不算失败、不占解锁或改密次数。
9. **`__Host-` 刷新 Cookie。** release 模式下刷新 Cookie 名为 `__Host-ga_rt_<端>`、`Secure`、`Path=/`、不带 `Domain`，浏览器不接受别的主机写入；代价是 Cookie 会随本主机的所有请求发送（仍是 `HttpOnly`、`SameSite=Strict`，服务端只在刷新时读）。debug 模式在本机 http 上开发，用 `ga_rt_<端>`、路径 `/api/<端>/v1/auth`。刷新时带了多个同名 Cookie 一律拒绝（401，不带"会话已结束"），记安全事件 `refresh_cookie_dup`。
10. **部署与文档。** 镜像设 `GA_SERVER_MODE=release`，本机调试显式传 debug；示例 nginx 加 `server_tokens off`，CSP 加 `object-src 'none'; base-uri 'self'; form-action 'self'`，加 COOP、Permissions-Policy，给出 HSTS 写法，并提示后台不要和不受信任的站点共用主域。新增模块指南的写操作示例在 `WithActor` 回调里写库，说明本人写操作用 `WithSelf`，并要求每条写接口补在途撤权、停用、吊销的反向用例（系统模块的逐路由用例不会自动覆盖新模块）。
11. **前端头像保存绑定身份。** 开始保存时记下登录身份代数和对话框的代次，裁剪完成后核对，关闭或卸载时作废。
12. **小问题。** 管理员建、改用户时显示名走 `cleanName`、简介走 `cleanBio`；用户、角色、字典、字典项的排序值上限 1000000（和部门、岗位、菜单一致）。

理由：审计记录是事后追查的唯一依据，不能因为攻击者控制的字节丢掉；账号在不在、被遮蔽的是谁，都不能靠响应的快慢或成败试出来；代码拥有的值后台改不了；交出权限的操作（分配角色、启用角色、启用账号）用同一套规则；任何人都能调的接口不能占用全端共用的资源。测试：§13.2 第 104–112 条。

## D-059 · 2026-10-01 · 操作日志请求体上限、本人写操作锁会话行、两处细节收紧

问题：
- 操作日志的请求体有 4 KB 上限，每个分支（JSON、表单、其他类型的占位符）都要守住；占位符里的类型名来自请求头，同样要截断。
- 本人写操作（`WithSelf`）和吊销会话谁先谁后，要由同一行上的锁决定，不靠读的时机。
- 重新启用账号被拒时，错误信息只给调用者有权知道的内容。
- 前端"待补退出"标记的 Cookie 和刷新 Cookie 一样，要防同主域的其他主机写入。

选择：
1. 操作日志中间件对请求体统一 `truncate(…, MaxBody)`（字符边界、合法 UTF-8），不再依赖每个分支各自截断；占位符里的类型名截到 64 字节。
2. `WithSelf` 先锁账号行、再锁会话行（`rbac.Options.LockSession`，由 app 接到会话表的 `LockActive`）。吊销写的是同一行，两边排队：吊销提交之后才轮到本人写操作，它看到"已吊销"回 401。加锁顺序"账号行 → 会话行"和改密、解锁、建会话一致；吊销单个会话、刷新、锁屏只锁会话行，不会反过来等账号行。
3. 重新启用账号被拒时只回 `rbac.user.enableNotAssignable`（"这个账号有你不能分配的角色"），不列具体内容。
4. https 下标记 Cookie 名为 `__Host-ga_lo_<端>`（`Secure`、`Path=/`、不带 `Domain`）；本机 http 开发用 `ga_lo_<端>`。不带前缀的名字在 https 下怎么处理见 D-060。

理由：写库的每一列都要有上限，靠每个分支各自记得截断迟早会漏；"吊销之后不会再有旧会话的写入提交"要靠同一行上的锁，而不是靠读的时机；错误信息只给调用者有权知道的。测试：§13.2 第 113–114 条；第 108 条断言通用错误键、不含具体权限码。

## D-060 · 2026-10-01 · https 下不带前缀的"待补退出"标记：只作不恢复的依据

问题："待补退出"标记的 Cookie 在 https 下叫 `__Host-ga_lo_<端>`，本机 http 开发时叫 `ga_lo_<端>`（D-059）。同一个站点先后经 http、https 访问，或前端判断的协议和部署不一致时，没确认的退出可能只记在不带前缀的名字里，只读带前缀的名字就会漏掉它，那个会话在这个浏览器里可能被恢复。可不带前缀的 Cookie 同主域的其他主机也写得进，不能凭它去吊销会话（D-059 要防的正是这个）。

选择：https 下另外读不带前缀的标记，只当"不恢复"的依据：启动时刷新换来的会话在这份标记里，就只清掉本地登录态、不恢复，也不发退出请求，标记留着（下次启动换来的还是它，照样不恢复；用户重新登录得到新会话后不再命中）；换来的会话不在里面，或刷新被服务端拒绝，这份标记就没有用了，删掉。新写的标记只写带前缀的名字。

说明：被塞进来的不带前缀的标记，最坏让受害者重新登录一次（前提是对方知道受害者当前的会话号），不会吊销任何会话。

理由：来源不可信的信号只能用来让系统更保守（不恢复），不能用来触发对别人有影响的动作（吊销）。测试：shell `store.https.test.ts`（jsdom 以 https 地址运行）。
