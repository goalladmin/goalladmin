# 密码哈希算法：选哪种、怎么设置

**不设置也能用。** 默认是 Argon2id，配置文件里什么都不用写。只有下面"选哪种"里提到的几种情况才需要改。

这里说的是"账号的密码存进数据库之前怎么算成哈希"。它不影响登录接口、不影响前端，换算法也不需要用户重置密码。规则的细节在[技术规范](../spec.md) §5.6，取舍的原因在[决策记录](../decisions.md) D-070、D-071、D-072。

## 选哪种

| 取值 | 算法 | 什么时候选 | 一次计算 |
|---|---|---|---|
| `argon2id`（默认） | Argon2id，内存 19 MiB、2 轮 | 没有特殊要求就用它：最快，抗显卡和专用芯片并行猜密码的能力最强 | 约 0.02 秒，占 19 MiB 内存 |
| `bcrypt` | bcrypt，cost 12 | 要和只认 bcrypt 的旧版本（v0.1.0）并存一段时间、要留回退的余地；或者机器内存很紧 | 约 0.2 秒 |
| `pbkdf2-sha256` | PBKDF2-HMAC-SHA256，60 万次 | 部署有 FIPS 140 要求（见下面"有 FIPS 140 要求的部署"） | 约 0.1 秒 |
| `pbkdf2-sha512` | PBKDF2-HMAC-SHA512，22 万次 | 同上，而且审计方或既有规范点名要 SHA-512 | 约 0.1 秒 |

耗时是 2 核机器上测的量级，换机器会变。每种算法的参数（内存、轮数、cost、迭代次数）是固定的，不提供配置。

没有上面这些理由，不要选后三种：它们算得更慢，对并行猜密码的抵抗力也不如 Argon2id（PBKDF2 最弱）。

## 怎么设置

配置键是 `server.passwordHash`，两种写法任选其一，环境变量优先：

```yaml
# server/config/config.yaml
server:
  passwordHash: bcrypt      # argon2id | bcrypt | pbkdf2-sha256 | pbkdf2-sha512
```

```bash
export GA_SERVER_PASSWORD_HASH=bcrypt
```

用仓库自带的 Docker Compose 部署时，写在 `deploy/.env` 里：

```bash
GA_SERVER_PASSWORD_HASH=bcrypt
```

改完重启程序生效。要注意的三点：

- 取值写错（大小写不对、多了空格、不在上面四个里）程序拒绝启动，报错里会列出可以取的值。它不会悄悄退回默认值。
- 平台、代理商、商户三个程序各读各的配置，**设成一样的**。不一致不会让谁登不上，只是账号在哪个程序登录，哈希就被换成哪个程序选的算法。
- 这个设置只决定**新写进去的**哈希用哪种算法；核对密码时四种都认，不看这个设置。

### 确认生效了

新建一个账号、或者让一个账号登录一次，然后看库里哈希的开头：

```sql
SELECT username, LEFT(password_hash, 16) FROM ga_user ORDER BY id DESC LIMIT 5;
```

| 开头 | 算法 |
|---|---|
| `$argon2id$` | Argon2id |
| `$2a$`（也认 `$2b$`、`$2y$`） | bcrypt |
| `$pbkdf2-sha256$` | PBKDF2-HMAC-SHA256 |
| `$pbkdf2-sha512$` | PBKDF2-HMAC-SHA512 |

## 换算法时，已有的密码会怎样

**不会失效。** 换了设置之后：

- 库里原来的哈希照常核对，用户用原来的密码照常登录。
- 账号**登录成功的那一次**，哈希被自动换成新选的算法（只换哈希这一列，"必须改密"、改密时间、会话都不动）。本人改密、管理员重置密码写进去的也是新选的算法。
- 一直不登录的账号，哈希一直留着原来的算法。

所以切换是逐步完成的。想知道还剩多少没换过来，按算法数一下（代理商、商户的账号在 `ga_agent_user`、`ga_merchant_user`，同样查）：

```sql
SELECT SUBSTRING_INDEX(password_hash, '$', 2) AS algo, COUNT(*) FROM ga_user GROUP BY algo;
```

四种之间怎么换、换几次都一样，包括换回默认值。

## 从 v0.1.0 升级

v0.1.0 只有 bcrypt，也只认 bcrypt 的哈希。升级到带这个设置的版本时：

1. **先升级平台程序**，它会执行迁移（把密码字段加宽）；再升级代理商、商户程序。
2. 用默认的 Argon2id 就**不能再降级，也不要新旧版本混着跑**：旧版本不认识 Argon2id 的哈希，升级之后建的、重置的、登录过的账号在旧版本上都登不上，还会被记成密码错误。同一个程序跑多个实例的，在一个时间窗口里全部换成新版本。
3. 需要新旧并存、或者想留回退余地的：先把 `passwordHash` 设成 `bcrypt` 再升级——这时新版本写进去的仍是旧版本认识的哈希；确认稳定之后再改回默认值。

## 机器够不够

登录、解锁、改密、建账号、重置密码都要做密码计算。同时在算的个数有上限 `server.passwordParallel`（环境变量 `GA_SERVER_PASSWORD_PARALLEL`）：默认 `0`，表示按 CPU 数取 `max(8, 4×核数)`；占满时登录和解锁最多等 2 秒，改密、建账号直接回"请稍后再试"。

- 用 Argon2id：每个在算的请求占 19 MiB，进程的内存峰值大约是"上限 × 40 MB"（2 核机器默认 8 个，约 320 MB）。内存小的机器按这个预留，或者把上限调小。
- 用 bcrypt、PBKDF2：不占大块内存，吃的是 CPU——一次 0.1～0.2 秒，一个核一秒只算得完几次到十次。
- 上限建议不小于 8：代理商端、商户端按主体限并发的个数是固定的，位置太少时一个主体就可能占满全部。

## 有 FIPS 140 要求的部署

`pbkdf2-sha256`、`pbkdf2-sha512` 是给这类部署准备的：PBKDF2 是 FIPS 140 批准的算法，这里只用 Go 标准库实现；Argon2id、bcrypt 不在批准之列。后端别处用到的密码学（随机数、SHA-256、HMAC-SHA256 的令牌签名）也都在标准库里。

**框架提供的是这个选项，不是认证。** FIPS 140 认证认的是密码模块，不是用它的程序。一个部署合不合规由部署的人和他的审计方判断，至少还要做这几件事：

1. **用认证过的密码模块版本构建。** Go 自带的密码模块有通过了 FIPS 140-3 认证的版本，构建时用 `GOFIPS140` 指定（例如 `GOFIPS140=certified`），这样构建出来的程序默认在 FIPS 模式下运行；也可以在运行时用 `GODEBUG=fips140=on` 打开。仓库里的 Makefile、镜像不带这个设置，要自己构建。哪些版本通过了认证、支持哪些平台，以 [Go 官方的说明](https://go.dev/doc/security/fips140)为准。
2. **把 `passwordHash` 设成 PBKDF2 的两种之一。** 框架不检查"FIPS 模式下选的是不是 PBKDF2"——选错了不会报错。
3. **处理库里已有的哈希。** 从别的算法换过来时，库里留着的 Argon2id、bcrypt 哈希在账号下一次登录时还会用原来的算法核对一次，然后才换掉。要严格的话：新装的系统从一开始就选 PBKDF2；已经在用的系统换过来之后，让还没换的账号重置密码（用上面那条按算法计数的 SQL 找出来）。
4. **数据库这一头。** 数据库账号用 `caching_sha2_password` 认证方式，程序到数据库的连接走 TLS。MySQL 驱动在别的情况下（老的 `mysql_native_password`，或不走 TLS 时的完整认证）会用到 SHA-1。
5. **程序之外的组件。** 反向代理的 TLS、数据库本身、操作系统，各有各的要求，不在框架的范围里。

## 常见问题

**改了设置，为什么库里大部分哈希还是原来的？** 哈希只在账号登录成功时换。见上面"换算法时，已有的密码会怎样"。

**能不能让一部分账号用一种、另一部分用另一种？** 不能按账号选。一个程序只有一个设置。

**密码最长多少？** 72 字节，选哪种算法都一样（一个汉字 3 字节）。

**别的系统导出的密码哈希能直接导入吗？** bcrypt（`$2a$`、`$2b$`、`$2y$`，cost 不超过 14）和通行写法的 Argon2id（内存不超过 64 MiB、不超过 8 轮、并行度不超过 4）可以直接放进 `password_hash`，登录后会换成当前的设置。PBKDF2 不行：各个系统存 PBKDF2 哈希的写法不一样，要先转成这里的写法（`$pbkdf2-sha256$i=<次数>,l=<输出字节数>$<盐>$<输出>`，盐和输出是不带填充的 base64），而且只认 SHA-256、SHA-512。
